# Runtime & Packaging Options for a Heavy Geologic Simulation in a Minecraft Mod

Scope: where/how a heavy grid-based geologic simulation (plate tectonics, erosion, sediment,
climate, ore genesis; ~1k²–16k² cells, thousands of time steps) could execute for a NeoForge
1.21.1 (Java 21) mod meant to work in Ben's ~190-mod "Minecraft Industrial Complex" pack and in
the wider public modding ecosystem, under cross-platform and dedicated-server constraints.
Research conducted 2026-09-27. Two mods already present in the MIC pack — `voicechat-neoforge`
(Simple Voice Chat) and `powergrid-mc1.21.1-0.6.1.jar` ("Create: Power Grid") — were opened and
their bytecode/strings inspected directly as primary evidence; these are cited as
`[Local jar inspection]` with the file's public repo where one was found.

## Pure JVM on Java 21: Vector API, threading, memory limits, numeric libraries

### Takeaway
On Java 21 the Vector API is still a JDK **incubator** module (`jdk.incubator.vector`, JEP 448,
sixth incubator) that requires the launch-time flag `--add-modules jdk.incubator.vector` — a flag
a mod cannot inject into its own already-started JVM, so it only works if the player's instance,
pack, or server startup script sets it explicitly. Default heap ceilings across the common
launchers (roughly 2–4 GB) are far below what a multi-GB, multi-layer 16k² grid needs, so a
mod would either need the pack/server operator to raise `-Xmx` (already normal for a 190-mod
pack) or keep simulation state off-heap. EJML and ojAlgo are mature, pure-Java, dependency-free
numeric libraries that would run anywhere the JVM does, at a performance cost relative to
native/SIMD code; JOML is ubiquitous in the modding classpath already (via LWJGL) but is a
graphics vector/matrix library, not a sparse-solver or grid-numerics library. At least one small
pure-Java hydraulic-erosion library (JOML-only dependency) already exists, showing the domain is
tractable in plain Java at smaller scales.

### Cited Findings
- The Vector API's Java-21 incarnation is JEP 448, "Vector API (Sixth Incubator)"; it continued incubating in JDK 22 (JEP 460, 7th), JDK 23 (JEP 469, 8th), JDK 24 (JEP 489, 9th) and JDK 25 (JEP 508, 10th) — it has never left incubator/preview status as of the JDK 25 JEP. — [JEP 448](https://openjdk.org/jeps/448); [JEP 460](https://openjdk.org/jeps/460); [JEP 469](https://openjdk.org/jeps/469); [JEP 489](https://openjdk.org/jeps/489)
- "Because the Vector API is still an incubating module, the JVM will not expose it unless you ask by adding it to your JVM arguments" — i.e. `--add-modules=jdk.incubator.vector` must be present at JVM launch. — [GitHub discussion, YouHaveTrouble/minecraft-optimization #71](https://github.com/YouHaveTrouble/minecraft-optimization/discussions/71)
- A real-world Minecraft-adjacent example (the Pufferfish server JAR / PaperMC-family launch scripts) sets this via a `JVM_OPTS_EXTRA=--add-modules=jdk.incubator.vector` environment variable at server-launch time, i.e. it is configured outside the mod/plugin itself, at the process-launch layer. — [WebSearch summary, jdk.incubator.vector modpack context](https://github.com/YouHaveTrouble/minecraft-optimization/discussions/71)
- JEP 508 (JDK 25) notes the Vector API's own reference implementation "now links to native mathematical-function libraries via the Foreign Function & Memory API (JEP 454) rather than custom C++ code inside the HotSpot JVM" — showing the Vector API and FFM are increasingly coupled under the hood. — [JEP 508](https://openjdk.org/jeps/508)
- Java 21 finalized **virtual threads** (JEP 444). Per the JEP and follow-on commentary: "if the workload is CPU-bound (image processing, cryptography, heavy computation), virtual threads will not help. Having more threads than cores does not give you more CPU cycles" — virtual threads are scheduled onto a dedicated `ForkJoinPool` sized to available processors and are designed for throughput on blocking/I-O-bound work, not to speed up compute-bound kernels. — [JEP 444](https://openjdk.org/jeps/444); [JavaSpecialists Issue 311](https://www.javaspecialists.eu/archive/Issue311-Virtual-Threads-and-Parallel-Streams.html)
- The default `ForkJoinPool.commonPool()` used by parallel streams is a separate pool (LIFO-mode) from the virtual-thread scheduler pool (FIFO-mode); both are sized off `Runtime.availableProcessors()`. — [JavaSpecialists Issue 311](https://www.javaspecialists.eu/archive/Issue311-Virtual-Threads-and-Parallel-Streams.html)
- Official Minecraft Launcher default max memory is commonly reported at **~2048 MB (2 GB)**. — [Minefort blog: "How to Allocate More RAM to Minecraft"](https://minefort.com/blog/how-to-allocate-more-ram-to-minecraft)
- Prism Launcher's documented default is **Minimum 512 MB / Maximum 4096 MB**. — [BisectHosting: "How to Allocate More RAM in the Prism Launcher"](https://help.bisecthosting.com/hc/en-us/articles/50075520613787-How-to-Allocate-More-RAM-in-the-Prism-Launcher)
- CurseForge app default max memory is reported inconsistently across sources as either **~4096 MB (4 GB)** or, in some accounts, ~2 GB depending on version — sources conflict and none is Overwolf/CurseForge's own documentation. — [Game Host Bros guide](https://www.gamehostbros.com/guides/games/minecraft/allocate-ram-in-curseforge); [GameWiki.blog](https://gamewiki.blog/how-much-ram-curseforge)
- The Modrinth App's default is reported (with hedging language, "should be set to") at **~2048 MB (2 GB)**. — [orbispatches.com FAQ aggregator](https://orbispatches.com/gaming-faq/how-do-i-allocate-more-ram-to-modrinth)
- For context, real modded-server RAM guidance: "a 50-mod light pack runs fine on 6 GB RAM, while a 200-mod kitchen-sink pack like ATM9 or Better MC wants 10 to 16 GB" — MIC, at ~190 mods, sits in that upper band, implying its players/server operators already run well above launcher defaults. — [OuiHeberg modded server guide 2026](https://www.ouiheberg.com/en/blog/minecraft-modded-server-guide)
- EJML is described as "one of the fastest single threaded [Java matrix] libraries" and "among the most stable and more memory efficient," with no external dependencies. — [EJML GitHub](https://github.com/lessthanoptimal/ejml); [EJML Performance wiki](https://ejml.org/wiki/index.php?title=Performance)
- ojAlgo is "100% pure Java source code and free from external dependencies," first released 2003, covering linear algebra/optimization including sparse-adjacent decompositions (EVD, SVD, Cholesky) and solvers. — [ojAlgo Wikipedia](https://en.wikipedia.org/wiki/OjAlgo); [ojAlgo linear-algebra-benchmark](https://github.com/optimatika/ojAlgo-linear-algebra-benchmark)
- JOML ("Java OpenGL Math Library") is a "high-performance, lightweight math library... particularly those using OpenGL, Vulkan, or LWJGL," providing vector/matrix/quaternion operations and explicitly avoiding allocation for garbage-free use in render loops — it is a 3D-graphics math library, not a general/sparse linear-algebra or PDE-grid toolkit. — [JOML GitHub](https://github.com/JOML-CI/JOML)
- A real pure-Java hydraulic erosion implementation exists: "Rainfall" (GitHub `Vehxx/Rainfall`) is "a Java implementation of a particle-based hydraulic erosion simulation algorithm that accepts a heightmap ... and returns a 2D array of floats," whose **only dependency is JOML**. — [WebSearch result summarizing Vehxx/Rainfall and its Go port setanarut/rainfall]
- `[Local jar inspection]` **Create Aeronautics'** physics engine ("Simulated," bundled as `dev.simulated_team.simulated.simulated-neoforge-1.21.1-1.3.2.jar` inside `create-aeronautics-bundled-1.21.1-1.3.2.jar` in the MIC pack) contains **no** `.so`/`.dll`/`.dylib`/native-loader entries anywhere in its jar (nor in the sibling `aeronautics` or `offroad` jars) — a real, currently-shipping rigid-body physics simulation for Create-based packs runs entirely on pure JVM code. — [Local jar inspection, MIC pack: `create-aeronautics-bundled-1.21.1-1.3.2.jar`]; project: [Creators-of-Aeronautics/Simulated-Project](https://github.com/Creators-of-Aeronautics/Simulated-Project)

### Inferences
- For a NeoForge 1.21.1 mod meant for general public packs, depending on the Vector API is impractical: it cannot self-enable, and asking arbitrary third-party pack authors to add a JVM flag is not a control the mod has. It is more viable as an **optional, curator-enabled fast path** for Ben's own MIC pack (which already controls its own JVM args) than as a baseline requirement for a publicly distributed mod, with a scalar-Java fallback required regardless.
- Given ~2–4 GB default heaps and the fact that MIC-scale packs already push users to 10–16 GB, the simulation should assume it will only get generous heap on packs/servers that have been explicitly tuned — and, more importantly, should consider **off-heap storage** (native/direct memory outside `-Xmx`, e.g. via `MemorySegment`/`ByteBuffer.allocateDirect`) for the large grids so that heap-limited default configurations aren't immediately OOM-killed just by allocating the state, independent of whether any native *code* is used.
- Virtual threads (JEP 444) are not a performance lever for the compute-bound core of this simulation (grid relaxation, flow routing, etc.); the realistic pure-JVM parallelism story is classic fixed-size thread pools / `ForkJoinPool` / parallel streams sized to physical cores, decomposing the grid into row-blocks or tiles.
- EJML/ojAlgo are credible for general dense/sparse linear algebra inside the simulation, but neither is a domain-specific geomorphology/tectonics engine — algorithm porting effort from the Python/C++ reference codes would still be substantial regardless of which JVM numeric library is chosen.

### Gaps
- No official Mojang/Overwolf/Modrinth documentation was found with authoritative default `-Xmx` numbers; all four launcher figures above come from third-party "how to allocate more RAM" hosting-provider articles, which are consistent with each other in kind but not primary sources, and the CurseForge figure is directly contradictory between two secondary sources.
- No data was found on whether any published Minecraft mod today actually ships Vector-API-accelerated code with a scalar fallback (the `VectorX` project found is a general Minecraft-hot-path optimizer, not evidence of a simulation-style workload).

## Native code: JNI/JNA/LWJGL loader/FFM, precedents, targets, store policy

### Takeaway
Shipping native code in a Minecraft mod is a well-worn, currently-live pattern — this research
directly inspected two mods already in the MIC pack (Simple Voice Chat, "Create: Power Grid") and
confirmed both ship real per-platform native binaries loaded via classic JNI-style
extract-and-`System.loadLibrary`, both with an explicit pure-Java fallback path, and both openly
documented in their own config/code that the native path is a portability trade-off. The FFM API
(the JEP 442/454 successor to JNI) is preview-only in Java 21 and needs `--enable-preview` at
**both** compile and run time from the **same** feature release — a strictly worse distribution
story than plain JNI for a Java-21-pinned mod, and it only becomes a final, no-flag API in Java 22+.
Real-world evidence also surfaced a concrete failure mode specific to dedicated/hosted servers:
a native accelerated solver in "Create: Power Grid" crashed with `SIGILL` on a generic QEMU
virtual CPU because it used instructions the virtualized CPU didn't expose.

### Cited Findings
- `[Local jar inspection]` **Simple Voice Chat** (`voicechat-neoforge-1.21.1-2.6.22.jar`) ships native codec libraries for **six** platform/arch combinations each: `natives/{linux,mac,windows}-{x64,aarch64}/libopus4j.{so,dylib,dll}`, and matching sets for `librnnoise4j`, `liblame4j`, and `libspeex4j` — i.e. a complete linux/mac/windows × x64/aarch64 native matrix. — [Local jar inspection]; project [henkelmax](https://github.com/henkelmax) (opus4j: [henkelmax/opus4j](https://github.com/henkelmax/opus4j))
- `[Local jar inspection]` The same jar contains **both** `NativeOpusEncoderImpl`/`NativeOpusDecoderImpl` classes **and** `JavaOpusEncoderImpl`/`JavaOpusDecoderImpl` classes (backed by a bundled pure-Java "concentus" Opus port), plus `NativeInitializer` classes per codec (`de.maxhenkel.opus4j.NativeInitializer`, etc.) — confirming a dual native/pure-Java-fallback architecture. — [Local jar inspection]
- A separate, independent project (`ggadon/opus4j`) implements the same Opus-for-Java problem using **JNA** instead of JNI, showing both approaches are used in practice in this exact niche. — [ggadon/opus4j](https://github.com/ggadon/opus4j)
- `[Local jar inspection]` **"Create: Power Grid"** (`powergrid-mc1.21.1-0.6.1.jar`) ships `native/linux/libpowergridNative7.so` and `native/windows/libpowergridNative7.dll` only — **no macOS binary at all** — for its C++ "Modified Nodal Analysis" (MNA) circuit solver. Its config class `CSolver` carries this developer-authored comment verbatim: *"Solver MNA backend. The native backend can provide platform-specific acceleration which usually improves performance, however it isn't portable and needs a special binary which might not be available for all platforms. Java backend is portable and always available as fallback."* The `NativeMNA` class's string table confirms the OS check is literally only `"linux"` / `"windows"` (plus `"Unsupported platform!"` and `"Native backend failed to load. Accelerated solver will not be available!"` messages), and that it extracts the bundled binary to a temp natives directory at runtime before `System.loadLibrary`. A parallel pure-Java `JavaMNA` class (with `BiCGSTABSolver`, `GMRESSolver`, `DirectSolver`) exists as the always-available fallback, selectable via a `SolverBackend` config enum (`JAVA` / `NATIVE`). — [Local jar inspection]; project [patryk3211/PowerGrid](https://github.com/patryk3211/PowerGrid)
- PowerGrid's native solver is written in **C++**, built via **CMake**: "To build the native acceleration binary, you need to have cmake and a working C++ compiler installed. The cmake executable location can be configured in `native/gradle.properties`." — [patryk3211/PowerGrid repo](https://github.com/patryk3211/PowerGrid)
- A real, closed GitHub issue on that same project ("Mod not working on a VM," #457) documents a **SIGILL crash caused by the native library** on a hosted/virtualized dedicated server: *"The native PowerGrid library is attempting to execute CPU instructions that are not available on the exposed virtual CPU."* Environment: Proxmox VM using QEMU's generic "QEMU Virtual CPU 2.5" model (PowerGrid 0.5.1, Forge 1.20.1). — [patryk3211/PowerGrid issue #457](https://github.com/patryk3211/PowerGrid/issues/457)
- `[Local jar inspection]` **Distant Horizons** (`DistantHorizons-3.2.0-b-1.21.1-fabric-neoforge.jar`) bundles third-party compression natives (`lz4-java`, `zstd-jni`) with an unusually broad matrix: `darwin/{aarch64,x86_64}`, `linux/{aarch64,amd64,i386,ppc64le,s390x}`, `win32/amd64`, even `aix/ppc64` — but this breadth belongs to the upstream, long-maintained lz4-java/zstd-jni projects, not to Distant Horizons' own CI. — [Local jar inspection]
- **Valkyrien Skies 2**'s physics engine is loaded via JNI; its own docs expose `VS_PREFER_JNI=true`, a `.vs-natives` directory / `java.library.path` mechanism, and a `VS_USE_MOCK_PHYSICS` environment variable implying a non-native ("mock physics") fallback mode exists. — [ValkyrienSkies/Valkyrien-Skies-2 issue #1001](https://github.com/ValkyrienSkies/Valkyrien-Skies-2/issues/1001)
- The general JNI-to-Bullet-Physics binding ecosystem (e.g. `Libbulletjme`, referenced alongside VS2 in search results) explicitly supports "Windows, Linux, and macOS on x86 and x86-64 architectures, as well as Linux on ARM and macOS on ARM," i.e. a full desktop matrix is achievable for a mature JNI physics binding. — [jturner65/Libbulletjme](https://github.com/jturner65/Libbulletjme)
- **Flashback** (the modern Replay-Mod successor) "comes with FFmpeg already included, eliminating the need for separate installation" and bundles "a renderer with FFmpeg bundled, writing MP4, WebM, WebP, GIF, PNG and EXR sequences" — i.e. it ships a full external native **executable**, not just a shared library, inside the mod distribution. Flashback requires "Minecraft 1.21 or later, the Fabric loader, Fabric API" (Fabric-only, not NeoForge as of the sources found). — [Flashback on Modrinth](https://modrinth.com/mod/flashback); [About Flashback](https://flashback-mod.com/about/)
- By contrast, the original **Replay Mod** required the user to separately install FFmpeg and manually point the mod at the executable path (e.g. `C:\ffmpeg\ffmpeg.exe`) via "Command Line Settings" in Render Settings — the older sidecar-process-as-separate-install pattern that Flashback's bundling approach superseded. — [Replay Mod forum thread #241](https://www.replaymod.com/forum/thread/241); [Replay Mod forum thread #776](https://www.replaymod.com/forum/thread/776)
- FFM (Foreign Function & Memory API) was a **preview** feature through JDK 21 (JEP 442, third preview) and became **final** in JDK 22 (JEP 454): "you must compile and run the code with preview features enabled, i.e., `javac --release 21 --enable-preview` ... and `java --enable-preview`." — [JEP 442](https://openjdk.org/jeps/442); [JEP 454](https://openjdk.org/jeps/454)
- Per JEP 12 (the general preview-features mechanism): preview-compiled class files get their minor version field set to `65535`, and "the Java compiler, as well as the JVM, must be of the same Java version that includes the preview feature you want to use" — a class compiled as a JDK 21 preview will not run on JDK 22+ (or any other feature release) even with `--enable-preview` supplied, and won't run on 21 without the flag either. — [JEP 12](https://openjdk.org/jeps/12); [Baeldung: Java Preview Features](https://www.baeldung.com/java-preview-features)
- The Minecraft Launcher itself bundles a **Microsoft build of OpenJDK** as its Java runtime (reported for both recent and 2026-era Java Edition releases) — i.e. players run on a standard, non-GraalVM OpenJDK distribution by default. — [itechguides.com: Minecraft OpenJDK guide](https://www.itechguides.com/can-i-run-minecraft-with-openjdk-java-version-guide-for-every-edition/)
- Modrinth's Content Rules prohibit content that "violate[s] the law, deceive[s] users, impersonate[s] others, cause[s] harm, or upload[s] data to a remote server without clear disclosure"; every submitted project gets moderator review against these rules before going public, and a malware-detector flag triggers "a manual code review from a technical moderator." There is no rule specific to compiled/native binaries as such. — [Modrinth Content Rules](https://modrinth.com/legal/rules); [macmyths.com on Modrinth malware incident](https://macmyths.com/is-modrinth-safe-what-the-malware-incident-means-for-minecraft-players/)
- CurseForge's automated moderation "detects third-party files and checks if they are included in a global list of third-party libraries/plugins which have already been approved for inclusion in modpacks"; bundled/override mods must be MIT/GPL-equivalent licensed (or have explicit permission) and must be "an official unmodified distributable from the authors." No rule specific to native binaries was found. — [CurseForge Moderation Policies](https://support.curseforge.com/support/solutions/articles/9000197279-moderation-policies)

### Inferences
- The existence of Simple Voice Chat and "Create: Power Grid" as currently-distributed, moderator-approved mods on both Modrinth and CurseForge is itself strong existence-proof that bundling per-OS `.so`/`.dll`/`.dylib` binaries is accepted practice on both platforms; neither platform's written policy singles out native code, but Modrinth's manual "technical moderator" review step for anything malware-flagged implies native binaries may draw extra scrutiny precisely because they're not directly diffable/auditable Java bytecode.
- Because FFM is preview-only on the Java 21 baseline NeoForge 1.21.1 requires, and preview classfiles are pinned to one exact feature release plus a mandatory flag at both compile and run time, **plain JNI (or JNA) is the more distributable native-interop mechanism on this target**, not FFM — FFM only becomes attractive once/if the mod's minimum supported Minecraft version moves to one requiring Java 22+.
- PowerGrid's own precedent — omit macOS, ship Linux+Windows only, and gate the accelerated path behind a config toggle with a portable Java fallback as the default expectation — is a directly transferable architecture for a geologic-simulation "fast path," especially since PowerGrid solves a structurally similar problem (large sparse numeric solve over a Create-style network/grid).
- The PowerGrid SIGILL/VM issue is a concrete warning specific to Ben's "dedicated servers" scenario: hosted Minecraft servers are overwhelmingly virtualized (see the Dedicated Servers section), and generic hypervisor CPU models often expose a conservative baseline instruction set (lacking e.g. newer AVX extensions) even when the physical host supports more — a native build that isn't compiled for a conservative baseline (or doesn't runtime-dispatch by detected CPU features) risks crashing exactly the audience (server operators) most likely to run a heavy background simulation.
- Given the target platform list (windows-x64, macos-arm64/x64, linux-x64/arm64), achieving Simple-Voice-Chat-level coverage (6 platform/arch combinations, all three OSes times two architectures) requires either a real cross-compilation/CI investment (matrix builds, likely needing an actual macOS runner for the Darwin targets, which is harder to cross-compile from Linux CI than Windows/Linux targets are from each other) or accepting PowerGrid-style partial coverage with a mandatory portable fallback.

### Gaps
- No documentation was found describing Simple Voice Chat's or opus4j's actual CI/build pipeline (e.g. GitHub Actions matrix, cross-compilation toolchain, whether Darwin targets are built on real Mac runners) — only the shipped output artifacts were inspected, not the build system that produced them.
- No explicit, official Modrinth/CurseForge policy text was found that addresses compiled native binaries or bundled executables (e.g. ffmpeg) as a distinct category from general malware/licensing rules; the conclusion that this is permitted rests on existence-proof (real approved mods doing it) rather than a written rule.

## WebAssembly in the JVM

### Takeaway
Chicory is a pure-Java, zero-native-dependency Wasm runtime under active 2026 development
(threads-proposal support, JPMS support, verified JDK 25 compatibility) and would run on any
standard JVM a Minecraft launcher provides — a real advantage over native code for portability.
GraalWasm, by contrast, requires the GraalVM distribution itself and explicitly does not run on
standard OpenJDK, which — combined with Minecraft's launchers bundling a standard (Microsoft)
OpenJDK — makes it impractical for a distributed mod without bundling an entire alternate JVM. No
evidence was found of any existing Minecraft mod using either Chicory or GraalWasm for gameplay
or simulation logic.

### Cited Findings
- Chicory is "a JVM native WebAssembly runtime" that "allows you to run WebAssembly programs with zero native dependencies or JNI... written entirely in Java." — [Chicory GitHub](https://github.com/dylibso/chicory); [chicory.dev](https://chicory.dev/)
- As of the 1.6.0-era 2026 status found: "Chicory 1.6.0 added support for the Java Platform Module System (JPMS), a directory-backed runtime-compiler cache ... enhanced support for the Wasm 'Threads' proposal (atomic fence instructions and atomic ops), increased Wasm spec conformance and verified compatibility with Java 25." — [JVM Advent, "Bring WebAssembly to the JVM," Dec 2025](https://www.javaadvent.com/2025/12/chicory-webassembly-on-the-jvm.html)
- Broader 2026 Wasm-ecosystem summary: "SIMD got performance within 2× of native on vectorisable code; threads + atomics got real parallelism," while general-purpose backend use is still limited by "unresolved threading support in WASI." — [javacodegeeks.com, "WebAssembly in 2026"](https://www.javacodegeeks.com/2026/04/webassembly-in-2026-where-it-has-landed-what-wasi-0-2-changes-and-why-java-and-kotlin-developers-should-pay-attention-now.html)
- GraalWasm "requires GraalVM environment and does not support standard OpenJDK... is the WebAssembly engine of GraalVM, implemented using the Truffle framework." — [WebSearch summary of graalvm.org/webassembly and graalvm.org/jdk22/reference-manual/wasm/](https://www.graalvm.org/webassembly/)
- No Minecraft mod using Chicory was found; the closest adjacent project is `feather-rs/quill`, "a WebAssembly-based plugin API for Minecraft servers" — but this is a Rust-based server (Feather), not a JVM/Forge/NeoForge mod, and is not built on Chicory. — [feather-rs/quill](https://github.com/feather-rs/quill)

### Inferences
- Chicory's "runs on any standard JVM" property makes it the only Wasm-in-JVM option structurally compatible with how Minecraft mods are actually deployed (into an existing, unmodified JVM the launcher started); GraalWasm's GraalVM requirement is disqualifying for the general-public-mod goal unless the entire distribution model changes (e.g., a companion app that itself runs on GraalVM, separate from the game process).
- Since a compiled-to-Wasm geologic simulation kernel (e.g., from the C++ fastscapelib) run through Chicory's interpreter or AOT-to-bytecode mode would sit somewhere between pure-Java and native-C++ performance, and no precedent exists in the Minecraft modding space, this path carries meaningfully higher engineering-risk/unknown-performance than either the pure-JVM or native-JNI paths, even though it would sidestep native-binary distribution and per-OS builds entirely (Chicory needs only one `.wasm` file for all platforms).

### Gaps
- No concrete throughput/latency benchmark comparing Chicory-interpreted or Chicory-AOT-compiled numeric code against equivalent native or pure-Java code was found (the "SIMD within 2× of native" figure is a general Wasm-ecosystem claim, not a Chicory-specific or Java-hosted benchmark).
- Whether Chicory's Wasm-SIMD support is usable from JVM-hosted Wasm modules today (vs. still landing) was not conclusively confirmed beyond the "enhanced support for the Wasm Threads proposal" note for 1.6.0; SIMD-specific Chicory status was not separately verified.

## GPU compute via Minecraft's graphics context and alternatives

### Takeaway
Minecraft creates its OpenGL context via LWJGL/GLFW as (at minimum) a 3.2 **core** profile,
forward-compatible context; on Windows/Linux with current drivers this typically negotiates up to
whatever high version the vendor driver supports (4.5/4.6), but macOS's OpenGL implementation has
been capped at **4.1** since Apple deprecated OpenGL/OpenCL in 2018 (WWDC, macOS Mojave) — and
compute shaders require GL 4.3+, so native compute shaders are categorically unavailable on
macOS's real OpenGL driver. A real, currently-used Minecraft rendering library (Veil, consumed by
Create Aeronautics) does use compute shaders and has documented compatibility failures on
lower-end GPUs. Sodium is trending toward requiring OpenGL 4.5/4.6 and has already dropped macOS
support. The credible way to get GPU compute independent of Minecraft's own GL context is a
separate compute backend (OpenCL via LWJGL's own bindings, or TornadoVM, which JIT-compiles Java
to CUDA/OpenCL/Metal and explicitly supports Apple Silicon) — but this is moot for dedicated
servers, which essentially never expose a GPU at all.

### Cited Findings
- To use an OpenGL ≥3.2 **profile** at all, the context must be created as 3.2+ (profiles were introduced with GL 3.2), typically via GLFW window hints `GLFW_CONTEXT_VERSION_MAJOR=3`, `GLFW_CONTEXT_VERSION_MINOR=2`, `GLFW_OPENGL_PROFILE=GLFW_OPENGL_CORE_PROFILE` (plus forward-compat on macOS). — [WebSearch synthesis of GLFW/LWJGL context-creation discussions](https://www.lwjgl.org/); [OptiFine issue #5739 on 3.2 core profile requirements](https://github.com/sp614x/optifine/issues/5739)
- Apple announced at WWDC in June 2018 that OpenGL and OpenCL were deprecated on macOS (Mojave, 10.14): "active development has ceased on OpenGL and OpenCL on the Mac, and the APIs will only get 'minor changes' going forward," with Metal/Metal Performance Shaders as the recommended replacement. — [AppleInsider, June 2018](https://appleinsider.com/articles/18/06/04/opengl-opencl-deprecated-in-favor-of-metal-2-in-macos-1014-mojave); [Phoronix](https://www.phoronix.com/news/Apple-Deprecates-OpenGL-OpenCL)
- Consequently: "Apple deprecated OpenGL in 2018 and capped macOS at OpenGL 4.1... compute shaders are part of OpenGL 4.3 and later specifications, [and] macOS's OpenGL 4.1 cap prevents native support for these features without translation layers or workarounds" (e.g., Zink-over-Vulkan plus a Metal translation layer). — [GitHub gist: "Running Minecraft on macOS with Zink + KosmicKrisp"](https://gist.github.com/lucamignatti/5312f5e937de2ba44256ecba6de54cc2)
- Veil, whose "most prominent consumer is Create: Aeronautics" (bundled in the MIC pack) for "airplane wings, glass panels, contrails, and other visual effects," has a real, filed compatibility bug where a specific **compute shader** (`veil:light/indirect_sphere`) fails to compile on an Intel UHD 620 integrated GPU due to a `readonly` keyword/syntax issue — direct evidence a shipping mod's compute-shader code path already has real-world hardware-compatibility failures on common lower-end GPUs. — [Creators-of-Aeronautics/Simulated-Project issue #1437](https://github.com/Creators-of-Aeronautics/Simulated-Project/issues/1437); [FoundryMC/Veil README](https://github.com/FoundryMC/Veil/blob/1.21/README.md)
- Sodium "officially supports graphics cards with up-to-date drivers compatible with OpenGL 4.5 or newer... macOS is no longer supported as of newer versions of Sodium. Upcoming versions of Sodium might require OpenGL 4.5 or 4.6, which will affect macOS." — [WebSearch synthesis of CaffeineMC/sodium issues #343, #531, #1591](https://github.com/CaffeineMC/sodium/issues/343)
- LWJGL ships its own OpenCL bindings (`org.lwjgl.opencl`) as an optional module: "This access is direct and high-performance... OpenCL is designed for parallel processing and can be setup to run on a computer's GPU... to unlock the GPU's multithreading potential for purposes other than graphics." — [LWJGL javadoc, org.lwjgl.opencl](https://javadoc.lwjgl.org/org/lwjgl/opencl/package-summary.html); [LWJGL/lwjgl3 GitHub](https://github.com/LWJGL/lwjgl3)
- TornadoVM (actively developed, 2.0 released) "JIT-compiles Java bytecode into NVIDIA CUDA, OpenCL C, and Apple Metal (MSL) at runtime, so your existing Java code runs on NVIDIA GPUs (via CUDA), AMD, Intel, and Apple Silicon GPUs, integrated GPUs, and multi-core CPUs," works with "JDK 21+ (currently JDK 21, JDK 25, JDK 26, and JDK 27)," is "a plug-in to your existing OpenJDK or GraalVM installation," and as of TornadoVM 2.0 is "available via Maven Central for seamless integration with existing Java codebases." If a code segment can't be accelerated, "execution falls back to the host JVM." — [TornadoVM GitHub](https://github.com/beehive-lab/TornadoVM); [TornadoVM docs](https://tornadovm.readthedocs.io/en/latest/); [foojay.io TornadoVM 2.0 getting-started](https://foojay.io/today/getting-started-with-tornadovm-2-0/)
- Aparapi (an older Java-to-OpenCL GPU framework) was "last updated September 30, 2022," effectively superseded by TornadoVM. — [WebSearch synthesis]

### Inferences
- Because TornadoVM opens its **own** compute backend (OpenCL/CUDA/Metal) rather than riding on Minecraft's own LWJGL/GLFW-created OpenGL context, it sidesteps the macOS GL-4.1 ceiling entirely — Metal backend support means TornadoVM (unlike a GL 4.3 compute shader) could in principle run the same accelerated kernel on Windows/Linux (via CUDA/OpenCL) and macOS (via Metal) from one Java codebase, at the cost of adding a heavyweight, actively-evolving dependency with its own JIT/bytecode-rewriting machinery to a mod's runtime — a materially bigger integration than "add a jar to the classpath."
- GPU compute of any kind is essentially a non-option for the dedicated-server / headless-generation use case (see Dedicated Servers section) since hosted servers overwhelmingly have no GPU — meaning any GPU-compute code path in the design must be strictly optional/client-only, with a CPU (JVM or native) path required as the only universally available option.
- Given Veil's own compute-shader compatibility bug on integrated GPUs, and Sodium's trend of dropping older-GL/macOS support outright, betting the *authoritative* simulation on GPU compute shaders inside Minecraft's own context would inherit both the macOS gap and a long tail of driver-specific failures on the Windows/Linux side too — better suited to an optional visualization/acceleration layer than the core deterministic computation.

### Gaps
- No source was found stating the exact OpenGL version Minecraft 1.21.1's `GameRenderer`/window-creation code specifically requests in its GLFW window hints (vs. the generally-known "3.2 core" baseline established around the 1.17 renderer rewrite); this is inferred from OptiFine/driver-compatibility discussions rather than read directly from Minecraft's own source in this session.
- No data was found on JOCL's (the separate Java-OpenCL-bindings project, distinct from LWJGL's own OpenCL module) current 2026 maintenance status.
- No confirmation was found of Iris (the shader-pack loader mod) itself issuing compute shaders, as distinct from shader packs it loads doing so; the Veil evidence is the only confirmed in-the-wild compute-shader user found.

## Python sidecar: bundling, sizes, startup, licensing, failure modes

### Takeaway
python-build-standalone (the engine behind `uv python install`) gives small, modern, statically-linked
per-platform Python distributions (30–60 MB compressed) with prebuilt wheels for real geoscience
packages like fastscapelib readily available — a meaningfully lighter path than it used to be.
goSPL (PETSc/MPI-based) is the opposite case: it is fundamentally an HPC-oriented, MPI-linked
package whose own docs describe platform-pinned dependency versions and "bring your own MPI"
constraints, making it a poor fit for bundling onto arbitrary player machines. Jep embeds CPython
directly into the JVM via JNI, avoiding a separate process at the cost of needing a
matching native build per Python version/platform. PyInstaller's `--onefile` mode is documented to
trigger antivirus false positives and adds startup-time extraction overhead; `--onedir` avoids the
extraction-at-runtime behavior that triggers AV heuristics. conda-pack environments are not
cross-platform-relocatable (a pack built on Windows cannot be unpacked on Linux/macOS), which adds
to per-OS CI burden similar to native binaries.

### Cited Findings
- "The install-only archives that uv downloads use the fastest available build configuration (typically PGO+LTO optimized) and weigh 30-60 MB compressed per platform. Dependencies like OpenSSL, SQLite, and zlib are statically linked or bundled, so the distributions need only a C library (glibc or musl on Linux) from the host system." — [python-build-standalone GitHub / pydevtools handbook](https://pydevtools.com/handbook/reference/python-build-standalone/)
- python-build-standalone "is maintained by Astral, the team behind uv... These distributions are portable and can be installed into any path... support Linux, macOS, and Windows with multiple platforms and architectures." — [astral-sh/python-build-standalone GitHub](https://github.com/astral-sh/python-build-standalone)
- "All stable versions of Fastscapelib-Python are available on PyPI as binary wheels for Linux, MacOS and Windows" — i.e. `pip install fastscapelib` does not require a compiler on end-user machines for the common platforms. — [Fastscapelib install docs](https://fastscapelib.readthedocs.io/en/latest/install.html)
- Building fastscapelib's Python bindings **from source**, by contrast, needs "pip, pybind11, xtensor-python (version 0.28 or newer) and scikit-build-core, plus a C++ compiler supporting C++17," with `--no-build-isolation` required because xtensor-python can't yet be installed via pip alone — relevant only if a platform lacks a prebuilt wheel. — [Fastscapelib install docs](https://fastscapelib.readthedocs.io/en/latest/install.html)
- goSPL "links against the user's MPI/PETSc/parallel-HDF5 stack at install time; a wheel would lock those bindings to a single MPI ABI." Its conda path ("recommended for fresh installs") is `mamba install -c geodels -c conda-forge gospl`; its pip path needs a pre-existing MPI/PETSc/HDF5 stack via `pip install --no-deps --no-build-isolation gospl`. Critically: "on macOS, goSPL is pinned to PETSc/petsc4py 3.21.x for correct MPI finalization, and OpenMPI is limited to 4.x due to MPI_Init failures with OpenMPI 5.x." — [goSPL install docs](https://gospl.readthedocs.io/en/latest/getting_started/installConda.html); [goSPL HPC install docs](https://gospl.readthedocs.io/en/latest/getting_started/installHPC.html)
- pyGPlates reached a pip/conda-installable 1.0.0 release (27 March 2025): "pyGPlates 1.0.0 supports both conda and pip installation," e.g. `conda create -n pygplates_py313 -c conda-forge python=3.13 pygplates`, with GDAL as a notable dependency automatically handled by conda. — [pyGPlates 1.0.0 release blog](https://www.gplates.org/news/2025-03-27-pygplates-1-0-0-released/); [pygplates on conda-forge](https://anaconda.org/conda-forge/pygplates)
- Jep "embeds CPython in Java through JNI (Java Native Interface)... is safe to use in a heavily threaded environment... When you create an Interpreter instance in Java, a Python interpreter will be created for that Java Interpreter instance and will remain in memory until the Interpreter instance is closed." Reported compatible with NumPy, SciPy, Pandas and other native-extension-using packages. Building/installing "require[s] the JDK, Python, and optionally numpy to be installed beforehand." — [ninia/jep GitHub](https://github.com/ninia/jep); [ninia.github.io/jep](http://ninia.github.io/jep/)
- GraalPy: "the latest GraalVM version (25.0.2, released January 2026) added compatibility patches for NumPy versions below 2.3." GraalPy's Python-C-API support "extends only to the API, not the binary interface (ABI), so extensions built for CPython are not binary compatible with GraalPy, and packages that use the native API must be built and installed with GraalPy" specifically. Reported as "geomean approximately 4x faster than CPython" on general benchmarks, with "93% of the 600 most popular PyPI packages" installable. — [GraalPy compatibility docs](https://www.graalvm.org/python/compatibility/); [bswen.com GraalPy vs PyPy 2026 benchmarks](https://docs.bswen.com/blog/2026-03-10-pypy-vs-graalpy-python-performance/)
- PyInstaller's `--onefile` mode "creates a single executable that extracts everything to a temporary folder at runtime, and this extraction behavior is one of the things that triggers AV heuristics"; `--onedir` mode (the actual PyInstaller default) "produces a folder... Since nothing needs to be extracted at runtime, the behavior looks less suspicious to AV software." The PyInstaller team "periodically updates the bootloader to reduce false positives" as vendors flag each new compiled bootloader. — [pythonguis.com FAQ on antivirus/PyInstaller](https://www.pythonguis.com/faq/problems-with-antivirus-software-and-pyinstaller/); [pyinstaller/pyinstaller issue #6754](https://github.com/pyinstaller/pyinstaller/issues/6754)
- conda-pack "only works when the os system types are the same between origin and target, meaning environments built on windows can't be relocated to linux" — a packed environment is not cross-platform; separate packs must be built per target OS. — [conda/conda-pack GitHub](https://github.com/conda/conda-pack)

### Inferences
- Of the three named scientific codes, **fastscapelib** (prebuilt cross-platform wheels, no MPI) is by far the most bundle-friendly for a sidecar approach; **goSPL** (hard MPI/PETSc coupling, platform-pinned versions, documented macOS-specific finalization issues) is the least — bundling goSPL onto arbitrary player machines via any of the standard packaging tools would likely require shipping a full, version-pinned conda/MPI stack per OS and would be fragile exactly where players' environments vary most (driver/OS versions, existing MPI installs conflicting).
- Jep's JNI-based embedding ties the sidecar to the same "native binary per platform/Python-version" burden as the native-code path (Section 2), just for the Python-embedding bridge rather than the simulation code itself; it does not avoid native-binary distribution, it relocates it.
- If a subprocess (rather than in-process embedding) is preferred, `python-build-standalone` + a pip-installable, wheel-backed package (fastscapelib) is the most "just works" combination found — closer in spirit to Flashback's bundled-ffmpeg-executable pattern than to PyInstaller-style single-exe freezing, and avoids PyInstaller's specific AV-flagging failure mode.
- GraalPy's ABI-incompatibility with CPython native extensions ("packages that use the native API must be built and installed with GraalPy") means it cannot simply reuse existing prebuilt NumPy/SciPy/fastscapelib wheels built for CPython — it would need its own compatible builds, undercutting its appeal as a drop-in embeddable Python for this specific dependency stack unless those specific packages are separately confirmed to work in the version pinned.

### Gaps
- No concrete startup-time (cold-start latency) figures were found for any of Jep, GraalPy, or a python-build-standalone-launched subprocess specifically; only PyInstaller's extraction-overhead behavior was documented qualitatively.
- No size/startup benchmark specific to conda-pack (as opposed to its general relocatability constraint) was found.
- License terms for redistributing python-build-standalone binaries, or for bundling fastscapelib/pyGPlates/goSPL themselves inside a Minecraft mod distribution, were not directly investigated in this pass and should be checked per-package before any redistribution decision.
- No precedent was found of an existing Minecraft mod spawning a bundled Python interpreter or scientific-computing subprocess; the closest analogues found are the ffmpeg-subprocess pattern (Replay Mod/Flashback, media rather than scientific computing) and general knowledge that "mods spawning arbitrary external processes" is uncommon in this ecosystem.

## Companion desktop app (WorldPainter/Amulet model)

### Takeaway
WorldPainter and Amulet both establish precedent for a standalone tool that produces/edits
Minecraft world data independently of any mod, then hands off a result the game (or a mod) reads
— WorldPainter via generating/importing terrain into its own project format and then exporting
real Minecraft world folders, Amulet via a version-spanning intermediate "construction format" for
moving chunk data between tools. Neither is a mod; both are separately installed and run outside
the game process entirely.

### Cited Findings
- "WorldPainter is a map generator, not an editor, and is designed for generating new maps which you then edit with other tools... WorldPainter's Import function will create a new WorldPainter world based on the landscape (terrain height and type and biome information, but no underground or above ground structures...) of an existing map. The Merge function will merge any changes you make back to the existing map." — [WorldPainter FAQ](https://www.worldpainter.net/doc/faq)
- "Amulet is a Minecraft world editor made by the Amulet Team... supports every version since Java 1.12 and Bedrock 1.7." Amulet "created the construction format, which is a file to store Minecraft chunk data to disk so that it can be loaded after closing the editor, passed between computers or users or even to other programs that support the construction format... can hold data for Java and Bedrock and all versions of each." Amulet "is a standalone application that interacts directly with the world files." — [Amulet Map Editor / SourceForge & GitHub release notes](https://sourceforge.net/projects/amulet-map-editor.mirror/); [Amulet-Team/Amulet-Map-Editor v0.6.3](https://github.com/Amulet-Team/Amulet-Map-Editor/releases/tag/v0.6.3)

### Inferences
- The WorldPainter/Amulet precedent supports a design where the heavy simulation runs in a fully separate process/application (not inside the Minecraft JVM at all, sidestepping every launcher-memory-limit and JVM-flag constraint above), which then writes a result the mod reads at world-creation time — at the cost of the "live in-game visualization during world creation" requirement being harder to achieve if the two processes aren't already coupled (WorldPainter/Amulet are edit-then-export tools, not live-during-worldgen visualizers).
- Both precedents chose a custom interchange file format (WorldPainter's own project format; Amulet's "construction format") rather than trying to directly manipulate a live Minecraft world/region-file format during editing — suggesting a similar custom format (e.g., a heightmap/strata-stack format distinct from Minecraft's region files) is the natural handoff point between a companion sim app and the mod's world-creation code.

### Gaps
- No information was gathered on WorldPainter's or Amulet's install size, startup time, or licensing — this section focused on the architectural precedent (separate app + interchange format) per the assigned scope rather than duplicating packaging analysis already covered for Python tooling above.
- Distribution mechanics (how players would discover, install and keep a companion app updated alongside the mod, and how the mod would detect/version-check its output) were not investigated.

## Dedicated servers: specs, headless runs, and streaming progress/history to clients

### Takeaway
Typical hosted modded-Minecraft servers are CPU-single-thread-bound, RAM-generous-but-finite (a
190-mod pack like MIC realistically needs on the order of 10–16 GB), essentially never have a GPU,
and are very often themselves virtual machines — reinforcing the native-code VM/CPU-ISA risk found
in Section 2. A close, already-real precedent for "run a heavy generation task headlessly on a
server with progress reporting" exists in the **Chunky** pregenerator mod: server-side long-running
task, boss-bar-style progress UI, and start/pause/continue/cancel commands usable from console or
RCON. RCON itself is a narrow, command/response text protocol (not a push/streaming channel) with
a hard 1446-byte outbound command-size limit; a JSON-RPC-over-WebSocket "server management
protocol" is reported to be superseding RCON in some later Minecraft server context, but this was
not confirmed to apply to the pinned 1.21.1 target.

### Cited Findings
- "For modded servers, you need 8-12GB+ of RAM... A 50-mod light pack runs fine on 6 GB RAM, while a 200-mod kitchen-sink pack like ATM9 or Better MC wants 10 to 16 GB. For 1 to 5 players, plan for at least 10 GB with 12 to 16 GB recommended." — [OuiHeberg modded Minecraft server guide, 2026](https://www.ouiheberg.com/en/blog/minecraft-modded-server-guide)
- "Minecraft is single-threaded for most calculations, so a processor with high single-thread frequency... makes much more difference than 8 cores at 2.5 GHz. More cores help a little, mostly for chunk loading and a few mod async tasks, but they don't fix the main-thread bottleneck." No GPU requirement is mentioned in server-hosting guidance; "SSD storage is mandatory." — [Server hosting requirements synthesis](https://gameteam.io/blog/minecraft-server-hosting-requirements-ram-cpu-storage-calculator/)
- Chunky: "Server-side tool that has some optional client features"; "When you start generation, you will see a progress bar at the top of your screen with a percentage complete and a rough time estimate of time remaining." Commands include `chunky start`, `chunky pause`/`chunky continue`/`chunky cancel`, `chunky progress` (display progress for all tasks), and `chunky silent`/`chunky quiet` to control update-message verbosity — usable on Fabric and Forge/NeoForge modded servers. — [Chunky Pregenerator on Modrinth](https://modrinth.com/mod/chunky-pregenerator); [MintServers Chunky commands guide](https://mintservers.com/knowledgebase/pre-generate-your-minecraft-world-with-chunky-stop-lag)
- RCON has "an outgoing (client to server) packet size limitation of 1460 bytes, with the maximum command size that can be sent being 1446 bytes. This limitation has no workaround and is an inherent issue with the RCON protocol itself." Its fundamental design is "sending a command string and getting console text back, rather than exposing typed methods and pushing notifications." A source claims Minecraft now additionally ships a "server management protocol: JSON-RPC 2.0 over a WebSocket, authenticated with a bearer token, TLS-encrypted by default" as an alternative to RCON. — [wiki.vg-derived RCON documentation summary](https://wiki.vg/RCON)
- `[Local jar inspection]` The PowerGrid VM/SIGILL crash (cited fully in Section 2) is direct, concrete evidence that native-accelerated numeric code can fail specifically in the hosted/virtualized-server environment that is the norm for "dedicated servers," even when it works fine on the developer's own bare-metal machine. — [patryk3211/PowerGrid issue #457](https://github.com/patryk3211/PowerGrid/issues/457)

### Inferences
- Chunky is the closest existing precedent for exactly the "run headless on a dedicated server, report progress to connected clients" requirement in the brief: a boss-bar/progress-message UI driven by server-side state, controllable via console or RCON commands, is a proven, currently-used UX pattern this mod could copy directly for the geologic simulation's server-side run.
- Because RCON is strictly request/response text (not a push channel) and payload-size-limited, any "watch the history stream live" feature for connected clients is better served by Minecraft's own existing client\<-\>server packet channel (custom mod packets carrying compact state/frame deltas, the same channel Chunky's own progress bar presumably uses) rather than by RCON — RCON is more suited to an external operator polling status than to in-game players watching a live simulation.
- Given "essentially never a GPU" and "single-thread-CPU-bound, sometimes virtualized" as the dedicated-server reality, the server-side authoritative simulation path should be designed around plain multi-core-CPU JVM (or conservatively-targeted/feature-dispatching native) code, never GPU compute, and should be defensive about CPU-ISA assumptions given the PowerGrid precedent.

### Gaps
- The claim that Minecraft now ships a JSON-RPC/WebSocket server management protocol superseding RCON was sourced from a single secondary summary (not Mojang's own release notes or wiki.vg's primary page content directly), and it is unclear whether this applies to the 1.21.1 version the mod targets (which predates 2026) or only to newer server versions — this should be treated as unconfirmed for the pinned target and re-verified against Mojang's own 1.21.1/later changelog before being relied upon.
- No figures were found for how large a "frame" of simulation state (for streaming/visualization purposes) would need to be at 1k²–16k² resolution, or what bandwidth budget a vanilla-protocol custom-packet channel realistically supports — this is a design question for the report writer, not something sourced here.

## Determinism: floating-point reproducibility and why it matters

### Takeaway
Java has required strict, platform-independent IEEE 754 floating-point semantics for **all**
code since JEP 306 landed in Java 17 (removing the old "non-strict by default" mode that could use
extended x87 precision) — meaning identical Java bytecode executing the same sequence of
operations gives bit-identical results on any conformant JVM/platform. That guarantee does **not**
extend across implementations that reorder or fuse operations differently: floating-point addition
and multiplication are not associative, so native/SIMD code (different vectorization, different
horizontal-reduction order, FMA usage) and especially GPU code (parallel, scheduler-order-dependent
reductions) can legitimately produce different bit patterns than a scalar Java reference doing the
"same" computation in a different order — this is a well-documented, actively-researched problem
in HPC/ML, not a Java-specific quirk.

### Cited Findings
- JEP 306 (targeted at JDK 17): "restore the original floating-point semantics to the language and VM, matching the semantics before the introduction of strict and default floating-point modes in Java SE 1.2... updating the HotSpot virtual machine to never run in a floating-point mode which allowed the extended exponent value set." Motivation given: "Intel and AMD processors have long supported SSE2... which allow natural support for strict floating-point semantics [so] the technical motivation for having a default floating-point semantics different than strict is no longer present." — [JEP 306](https://openjdk.org/jeps/306)
- "Floating-point arithmetic is not associative. GPUs run additions in parallel and in a non-deterministic order, so the same computation can yield slightly different results each run — even at temperature=0 [in an LLM-inference context, illustrating the general principle]." "The unpredictable states of the memory hierarchy and various heuristic-based GPU schedulers cause threads to be scheduled in a non-deterministic manner, which affects the order of operations." — [arXiv 2408.05148, "Impacts of floating-point non-associativity on reproducibility for HPC and deep learning applications"](https://arxiv.org/pdf/2408.05148)
- Forcing deterministic GPU reductions (e.g. via atomics or fixed accumulation order, such as a "Reproducible Floating-point Accumulator") is possible but "can cost an almost 2x slowdown," and one practical fix is to make "the complete floating-point reduction order... a pure function of the problem shape by fixing kernel configurations and combining partial sums in a fixed ascending order with no atomics." — [arXiv 2408.05148](https://arxiv.org/pdf/2408.05148); [NVIDIA developer blog on controlling FP determinism](https://developer.nvidia.com/blog/controlling-floating-point-determinism-in-nvidia-cccl)
- `[Local jar inspection]` PowerGrid's own dual-backend design (Section 2) documents the native/Java choice purely as a **portability/performance** trade-off ("Java backend is portable and always available as fallback") — its shipped config comment makes no claim that the native and Java solver backends produce matching numeric results, i.e. a real, mature Create-ecosystem mod doing comparable heavy numerics did not treat native/Java cross-consistency as a requirement to document or guarantee. — [Local jar inspection]

### Inferences
- Pure scalar Java (strict since 17, so unconditionally strict on the Java-21 baseline) is the only one of the runtime options researched here that gives a strong, standards-based bit-reproducibility guarantee across different players'/servers' machines for a fixed seed and fixed code — which directly serves the "seed sharing, multiplayer" motivation named in the brief, since every peer would need to run the identical instruction sequence, not just "the same algorithm."
- Any use of the Vector API, native SIMD/C++ code, or GPU compute for the *authoritative* history generation therefore risks breaking cross-machine/cross-platform reproducibility even if each individual op is IEEE-754-compliant, purely because vectorized/parallel code very likely sums or combines values in a different order than scalar code does. This implies an architecture where accelerated code paths (Vector API, native, GPU) are either: (a) used only for client-side visualization/preview rather than the seed-authoritative result, (b) used but their exact operation order pinned/audited to match the scalar reference bit-for-bit (achievable but with real performance cost, per the arXiv/NVIDIA sources), or (c) the authoritative result is computed once (e.g., server-side or by whichever peer starts the world) and distributed as data to other clients rather than independently recomputed by each peer from the seed.
- The PowerGrid precedent (no cross-backend determinism guarantee even attempted) suggests this is a genuinely hard, often-skipped problem in the Minecraft modding ecosystem — Ben's project would be unusual in the space if it explicitly solved it, which is itself worth flagging to the report writer as either a selling point (world seeds are truly portable/shareable) or an acceptable scope cut (ship computed data, not recomputable seeds) depending on how central seed-sharing is to the mod's value proposition.

### Gaps
- No source specifically addressing whether Java's Vector API (`jdk.incubator.vector`) preserves strict left-to-right IEEE 754 semantics for reduction-style operations (e.g. summing a vector lane-wise) in a way that's bit-identical to an equivalent scalar loop was found; this would need direct testing or a dedicated JEP/spec read beyond what surfaced in this search pass.
- No Minecraft-specific precedent (a mod that explicitly ships and documents a cross-platform-deterministic simulation, or one that explicitly gave up on determinism) was found beyond the PowerGrid omission noted above; this may be a genuinely novel design point for Ben's mod rather than one with existing modding-community prior art.
