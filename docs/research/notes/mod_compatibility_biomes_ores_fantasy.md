## Key question 1 — TerraBlender: how Regions add biomes, surface-rule injection, and what happens with a custom generator

### Takeaway
TerraBlender is a **Java-code API + 11 Mixins** library (not datapack/JSON-driven). Mods register `Region` objects (Java objects, weight + biome list) and namespace-keyed `SurfaceRules.RuleSource` trees via static registries (`Regions`, `SurfaceRuleManager`); a mixin into `Climate.ParameterList` builds a per-region-type 2D "uniqueness" area (reusing Minecraft's pre-1.18 zoom/layer noise algorithm) that macro-partitions the world X/Z plane by weight, then does a normal climate-parameter R-tree search *within* whichever region owns that cell. Applicability is gated by **`DimensionType` tags** (`terrablender:overworld_regions`, `terrablender:nether_regions`, both data-driven with `"replace": false`) combined with **`instanceof NoiseBasedChunkGenerator`** and **`instanceof MultiNoiseBiomeSource`** checks — not by dimension key or noise-settings resource ID. This means option (i) (keep `NoiseBasedChunkGenerator`+`MultiNoiseBiomeSource`, feed simulated values into the noise router) fully preserves TerraBlender compatibility; option (ii) (replace the concrete classes) silently disables all TerraBlender-based region/surface-rule injection for every dependent mod at once, unless the replacement classes still are/wrap `MultiNoiseBiomeSource`/`Climate.ParameterList`.

### Cited Findings
- TerraBlender's own wiki: "TerraBlender provides compatibility between biome mods by assigning each mod its own region in which they can define the biomes they wish to generate" and "regions are selected randomly during world generation according to their weight." [Source](https://github.com/Glitchfiend/TerraBlender/wiki/Getting-Started)
- `terrablender.api.Region` (abstract class, GitHub branch `1.21.1`): constructed with `(ResourceLocation name, RegionType type, int weight)`; subclasses override `addBiomes(Registry<Biome> registry, Consumer<Pair<Climate.ParameterPoint, ResourceKey<Biome>>> mapper)` and call `addBiome(...)` helpers that build a `Climate.ParameterPoint` from the **same six vanilla climate parameters** (temperature, humidity, continentalness, erosion, weirdness, depth) plus offset — i.e. region biomes are added into the identical 6-D space vanilla uses, not a 7th dimension `(verified via GitHub: Glitchfiend/TerraBlender, path Common/src/main/java/terrablender/api/Region.java, ref=1.21.1)`. Also defines `DEFERRED_PLACEHOLDER`, a sentinel biome meaning "fall back to the default/vanilla region here."
- `terrablender.api.RegionType` is a plain 2-value enum: `OVERWORLD, NETHER` — **no END member** `(same source, RegionType.java)`.
- `terrablender.api.Regions` is a **static, in-memory Java registry**, not datapack JSON: `register(ResourceLocation, Region)` / `register(ResourceLocation, int index, Region)` insert into a `LinkedHashMap<RegionType, LinkedHashMap<ResourceLocation, Region>>`; a static initializer auto-registers `DefaultOverworldRegion`/`DefaultNetherRegion` (vanilla's own biome layout wrapped as a Region) with config-adjustable weights `vanillaOverworldRegionWeight`/`vanillaNetherRegionWeight` `(same source, Regions.java)`.
- The "uniqueness" mechanism, `terrablender.mixin.MixinParameterList` (`@Mixin(Climate.ParameterList.class)`): `initializeForTerraBlender(RegistryAccess, RegionType, long seed)` builds `this.uniqueness` (a 2-D `Area`, via `LayeredNoiseUtil.finalUniqueness`) and one `Climate.RTree` per registered region (`uniqueTrees[regionIndex]`, built by calling that region's own `addBiomes`); `getUniqueness(x,y,z)` returns `this.uniqueness.get(x,z)` — **explicitly 2-D, Y is ignored**; `findValuePositional(target,x,y,z)` looks up the owning region for that X/Z via `getUniqueness`, R-tree-searches that region's own biome set for the climate point, and falls back to region-index-0's tree (the default/vanilla region) if the winning biome is `Region.DEFERRED_PLACEHOLDER` `(verified via GitHub source read directly, MixinParameterList.java, and independently re-confirmed by a decompile of the released terrablender-4.1.0.8.jar — both agree field-for-field)`.
- `terrablender.mixin.MixinChunkGenerator` (`@Mixin(ChunkGenerator.class)` — the **abstract base class**): injects at `HEAD` of `validate()` and unconditionally cancels it, to stop vanilla's "every biome reachable" assertion from running before modded biomes are injected `(verified via GitHub source, MixinChunkGenerator.java, and cross-confirmed in the decompiled 4.1.0.8 jar)`.
- `terrablender.mixin.MixinMultiNoiseBiomeSource` (`@Mixin(MultiNoiseBiomeSource.class)`): injects at `HEAD` of `getNoiseBiome(int,int,int,Climate.Sampler)`, cancellable, replacing vanilla's plain climate search with `findValuePositional(sampler.sample(x,y,z), x, y, z)` — biome choice becomes position-dependent, not climate-point-only `(decompiled terrablender-4.1.0.8.jar via sub-agent research, cross-checked against the Common-module mixin package listing I fetched directly from GitHub)`.
- `terrablender.mixin.MixinNoiseGeneratorSettings` (`@Mixin(NoiseGeneratorSettings.class)`): injects at `HEAD` of `surfaceRule()`, cancellable; if a `RuleCategory` was set on the instance, returns `SurfaceRuleManager.getNamespacedRules(category, originalRule)` instead of the vanilla rule tree `(decompiled 4.1.0.8.jar)`.
- `terrablender.api.SurfaceRuleManager` (read in full, GitHub `1.21.1` branch): a static registry keyed by `RuleCategory {OVERWORLD, NETHER, END}`. Mods call `addSurfaceRules(RuleCategory, String namespace, SurfaceRules.RuleSource rules)` to register their own namespace's rule tree, or `addToDefaultSurfaceRulesAtStage(RuleCategory, RuleStage {BEFORE_BEDROCK, AFTER_BEDROCK}, int priority, RuleSource)` to splice rules into the default tree at a given stage/priority. `getNamespacedRules(category, fallback)` builds a `NamespacedSurfaceRuleSource(fallback, {"minecraft": <default rules for category>, <each registered namespace>: <its rules>})` — i.e. it dispatches per-column surface rules by **which mod's biome namespace occupies that column** `(verified via GitHub: Common/src/main/java/terrablender/api/SurfaceRuleManager.java, ref=1.21.1, full file read)`.
- `terrablender.mixin.MixinBuiltInRegistries` registers `NamespacedSurfaceRuleSource.CODEC` under registry name **`terrablender:merged`** into `Registries.MATERIAL_RULE` when that registry bootstraps — this is the codec that lets a single JSON `"type": "terrablender:merged"` surface-rule entry stand in for "all mods' namespaced rules, merged" (decompiled 4.1.0.8.jar).
- Gating mechanism (the exact answer to "does it key on `minecraft:overworld` or the dimension?"): `terrablender.DimensionTypeTags` defines `OVERWORLD_REGIONS = TagKey.create(Registries.DIMENSION_TYPE, "terrablender:overworld_regions")` and `NETHER_REGIONS = "terrablender:nether_regions"`; default tag data `data/terrablender/tags/dimension_type/overworld_regions.json = {"replace": false, "values": ["minecraft:overworld"]}` (and `the_nether` for the nether tag). `terrablender.util.LevelUtils.getRegionTypeForDimension(Holder<DimensionType>)` returns `NETHER`/`OVERWORLD` based on tag membership or `null` (no blending) otherwise; applicability additionally requires the chunk generator to be `instanceof NoiseBasedChunkGenerator` with biome source `instanceof MultiNoiseBiomeSource` (`TheEndBiomeSource` is special-cased unconditionally). Grepping all decompiled TerraBlender source for the literal string `"minecraft:overworld"` found exactly one hit, in `terrablender.worldgen.DefaultOverworldRegion` — it is only the registry name of TerraBlender's own built-in fallback Region (used for the F3 debug label), **not** a dimension/noise-settings gate. **Practical implication: a custom dimension does not need to reuse vanilla's noise-settings ID to get TerraBlender support — it needs its `DimensionType` added to the `terrablender:overworld_regions`/`nether_regions` tag (a `"replace": false` datapack tag any mod can extend) and a generator that is concretely `NoiseBasedChunkGenerator` + `MultiNoiseBiomeSource`.** (All of this paragraph verified by decompiling the released `terrablender-4.1.0.8.jar` (the actual Modrinth 1.21.1 NeoForge build) with cfr — full sources read for `LevelUtils`, `DimensionTypeTags`, and the tag JSON.)
- Initialization order: `terrablender.core.TerraBlenderNeoForge` registers `NeoForge.EVENT_BUS.addListener(EventPriority.LOWEST, InitializationHandler::onServerAboutToStart)`, which iterates every `Registries.LEVEL_STEM` and initializes region blending per-dimension. `LOWEST` priority guarantees this runs after every other mod's `Regions.register(...)` calls (decompiled 4.1.0.8.jar).
- TerraBlender's own `terrablender.toml` config exposes `general.overworld_region_size`/`nether_region_size` (zoom-layer counts controlling patch size, default 3/2) and the vanilla-region weights (default 10/10 for overworld/nether; End sub-categories highlands/midlands/edge/island default size 4/4/3/2, weight 10 each) — these are the literal knobs behind "region weights" (decompiled 4.1.0.8.jar).
- BOP and BWG genuinely use the Region API (not just a nominal dependency): BOP ships `biomesoplenty/worldgen/BOPOverworldRegionPrimary.class`, `BOPOverworldRegionSecondary.class`, `BOPOverworldRegionRare.class`, `BOPNetherRegionCommon.class`, `BOPNetherRegionRare.class` (5 weighted Region subclasses); BWG ships `net/potionstudios/biomeswevegone/world/level/levelgen/biome/BWGTerraBlenderRegion.class` (verified in `terrablender/bop/biomesoplenty-21.1.0.14.jar` and `bwg/otbwg-2.6.0.jar`, scratchpad `.../scratchpad/r5/{bop,bwg}/`, via sub-agent jar inspection).
- A historical TerraBlender changelog entry states "Removed now unnecessary chunk generator mixin" (version 1.19.2-2.0.1.136) — confirming TerraBlender has iterated on chunk-generator compatibility internally over time rather than via an external bridge mod. [Source](https://modrinth.com/mod/terrablender/version/2.0.1.136)
- The newer TerraBlender default branch (`26.3`, likely targeting MC ≥1.21.3) adds one more mixin not present in the `1.21.1` branch/the `4.1.0.8` jar: `MixinChunkGeneratorBiomeSource.java` (filename only, not read) — noted as a forward-looking detail, not applicable to the MC 1.21.1 target. [Source](https://github.com/Glitchfiend/TerraBlender)

### Inferences
- Because `MixinChunkGenerator` targets the **abstract** `ChunkGenerator` base class (which any custom generator must still subclass to be constructible through Minecraft's codec/registry system), that one specific mixin (disabling `validate()`) would likely still attach even under option (ii). But the biome-placement and surface-rule mixins target the **concrete** `MultiNoiseBiomeSource` / `Climate.ParameterList` / `NoiseGeneratorSettings` classes — these only fire if option (ii)'s replacement actually is (or internally delegates to) those concrete vanilla classes. A fully from-scratch `BiomeSource` with no relationship to `MultiNoiseBiomeSource` severs all TerraBlender-based biome/surface-rule mods simultaneously — not selectively, since the gate is architectural (`instanceof`), not per-mod.
- The macro-scale region partitioning is purely a function of `(x, z, seed, weights)` via 2-D `Area` noise — it does not read Y at all and does not read the simulation's climate outputs. This means feeding simulated climate values into the noise router's temperature/vegetation/continentalness/erosion/weirdness/depth density functions (option i) changes *which biome wins inside a region* but does not change *which region owns a given X/Z cell* — TerraBlender's own region tessellation is orthogonal to and unaffected by simulation-driven climate.

### Gaps
- The exact codec/JSON shape TerraBlender uses for a standalone `"type": "terrablender:merged"` surface-rule datapack entry (as opposed to the Java-side `addSurfaceRules` call) was not read line-by-line.
- Whether `MixinBiomeSource`'s `appendDeferredBiomesList` (adding TerraBlender biomes to any `BiomeSource`'s "possible biomes" list) has any effect under option (ii) for a wholly custom `BiomeSource` was not tested.

## Key question 2 — Terralith, Terralith ReStoned, Tectonic, and Lithostitched (the exact jars in the MIC pack)

### Takeaway
**None of these three terrain mods use TerraBlender.** Terralith 2.6.2 and Tectonic 3.0.26 both ship **full-file overrides** of `data/minecraft/worldgen/noise_settings/overworld.json` and (for Terralith) `data/minecraft/worldgen/multi_noise_biome_source_parameter_list/overworld.json`, at the exact vanilla resource IDs — this is "last-pack-wins" replacement, not additive layering. Both hard-depend on **Lithostitched**, a 346-class shared library that extends vanilla's own `MultiNoiseBiomeSourceParameterList`/`MultiNoiseBiomeSource` **codecs via Mixin** to support a JSON-driven biome-injector/region system, and that patches ~50 vanilla worldgen classes (`NoiseBasedChunkGenerator`, `MultiNoiseBiomeSource`, `Climate.ParameterList`, `SurfaceRules.Context`, `NoiseGeneratorSettings`, `DensityFunctions$*`, several structure classes) via Mixin. Terralith's Skylands (floating islands) are produced by a **density-function spline** gated on a narrow band of the *same* six climate parameters, paired with a **matching multi-noise biome-parameter entry** — both mechanisms are used together and hand-tuned to overlap exactly. Tectonic+Terralith compatibility is achieved via **hand-authored, pairwise NeoForge datapack overlays** (`neoforge:mod_loaded` conditions), not a generic bridging system — this does not extend to unknown third-party mods.

### Cited Findings

**Terralith 2.6.2** (`Terralith_1.21.1_v2.6.2_Neoforge.jar`):
- Ships full replacements at the vanilla resource IDs: `data/minecraft/worldgen/noise_settings/overworld.json` (513 KB) and `data/minecraft/worldgen/multi_noise_biome_source_parameter_list/overworld.json` (970 KB), plus ~25 files under `data/minecraft/worldgen/density_function/overworld/*` and `.../noise_router/*` (`base_erosion`, `effective_continentalness`, `erosion`, `factor`, `jaggedness`, `offset`, `sloped_cheese`, `temperature`, `vegetation`, and the noise-router's `barrier`, `continents`, `depth`, `erosion`, `final_density`, `fluid_level_floodedness`, `fluid_level_spread`, `initial_density_without_jaggedness`, `lava`, `ridges`, `temperature`, `vegetation`, `vein_gap`, `vein_ridged`, `vein_toggle`) — all at vanilla `minecraft:` resource IDs (verified in `Terralith_1.21.1_v2.6.2_Neoforge.jar`, `unzip -l`).
- Its own namespace (`data/terralith/worldgen/density_function/overworld/...`) adds ~60 more density functions organized by feature: `arch/`, `archd1/`, `archmeme2/` (floating land arches), `cliff/`, `cliff_cringe/`, `dune/`, `dune2/`, `spike/`, `spikes/`, `special/caldera_*`, `special/crater_*`, `reference/{cave_cheese,megacave,pillars,surface_y,total_cheese}`, `link/aquifer_*`, and **`skylands/noise.json`** (verified, same jar).
- **`terralith.mixins.json`** exists but its `"mixins"` array is **empty** — Terralith ships **zero mixins of its own** in 2.6.2; the mod's config-toggle mechanism uses plain NeoForge features instead (below) `(verified: unzip -p ... terralith.mixins.json)`.
- Feature toggles use the **standard NeoForge datapack-overlay mechanism**, not mixins or hacks: `pack.mcmeta`'s `"neoforge:overlays"` section conditionally activates directories like `disable.skylands/`, `disable.custom_structures/`, `enable.vanilla_stone_gen/` via a custom `ICondition` type `"terralith:config"` (e.g. `{"directory": "disable.skylands", "neoforge:conditions": [{"type": "terralith:config", "key": "skylands", "invert": true}]}`). The condition is implemented by `net.stardustlabs.terralith.ConfigResourceCondition`, a Java `record` implementing `net.neoforged.neoforge.common.conditions.ICondition`, whose `test()` calls `ConfigHandler.getState().test(key)` `(verified: decompiled `ConfigResourceCondition.class` with `javap -p -c`, and read `pack.mcmeta` directly, same jar)`.
- **`META-INF/neoforge.mods.toml`** declares exactly one mod dependency: `[[dependencies.terralith]] modId = "lithostitched", type = "required", versionRange = "[1.7.7,)"` — Lithostitched is **mandatory**; NeoForge will refuse to load Terralith at all without it present `(verified, same jar)`.
- **The biome-parameter-list file is not standalone-valid vanilla JSON.** Parsing `data/minecraft/worldgen/multi_noise_biome_source_parameter_list/overworld.json` shows its top-level keys are `preset` (`"minecraft:overworld"`), `"lithostitched:migration_biome"` (`"terralith:cave/mantle_caves"`), and **`"lithostitched:biomes"`** (a 1713-entry array) — there is **no plain `"biomes"` key**, which is vanilla's own schema field name. This exactly matches Lithostitched's `MNBSPLMixin` (below), which adds `"lithostitched:biomes"` and `"lithostitched:migration_biome"` as extra optional codec fields on top of vanilla's `MultiNoiseBiomeSourceParameterList` codec `(verified: extracted and parsed the JSON directly with Python, same jar)`.
- **Skylands mechanism, precisely confirmed with matching numbers on both sides:**
  - Density function (`data/terralith/worldgen/density_function/overworld/skylands/noise.json`): a nested `minecraft:spline` keyed on `overworld/continents` → `overworld/erosion` → `overworld/vegetation` → `overworld/temperature` → `overworld/ridges` → `y`, which only produces a large positive bump (up to +1.25) around **y≈200–230** when continentalness ∈ [-0.745,-0.455], erosion ∈ [-0.223,-0.0865], vegetation ∈ [-0.1,0], temperature ∈ [-0.45,-0.3], ridges > 0.1 — i.e. it pokes a floating landmass at high Y regardless of the (ocean-like) base terrain in that column, gated on a narrow slice of the same climate parameters (verified, same jar).
  - Biome parameter list (`lithostitched:biomes` array): exactly 4 entries with `"biome"` = `terralith:skylands_{winter,autumn,spring,summer}`, parameters `weirdness:[0.19,1]`, `continentalness:[-0.745,-0.455]`, `erosion:[-0.2225,0.05]`, `depth:[-0.005,0]`, with temperature/humidity split by season — the continentalness/erosion ranges are the **same band** the density function uses (verified, same jar, parsed with Python).
  - **Conclusion: floating terrain here is produced by *both* mechanism (2) (density-function/noise-settings override) *and* mechanism (1) (biome-parameter-space placement) simultaneously and deliberately kept in sync by the author** — not by one mechanism alone.
- Terralith is packaged as `modLoader = "javafml"` (a normal coded mod), authors "Starmute, catter1, Apollo, TheKingWhale" (verified, `neoforge.mods.toml`).

**Terralith ReStoned 1.3.1** (`Terralith_ReStoned_v1.3.1.jar`, 9.5 KB):
- A **pure data-only addon**: `modLoader="lowcodefml"` (NeoForge's no-code datapack-as-mod loader), `[[dependencies]] modId="terralith", type="required", versionRange="[2.0,)", ordering="AFTER"`. Its entire payload is six vanilla `placed_feature` overrides — `ore_andesite_lower.json`, `ore_andesite_upper.json`, `ore_diorite_lower.json`, `ore_diorite_upper.json`, `ore_granite_lower.json`, `ore_granite_upper.json` — at the exact vanilla `data/minecraft/worldgen/placed_feature/...` IDs, restoring vanilla's normal andesite/diorite/granite stone-blob generation that Terralith's own terrain replacement otherwise removes/alters (verified, full `unzip -l` + `neoforge.mods.toml` read, same jar). **This is itself a concrete, minimal example of the "suppress/replace a mod's placed feature" mechanism relevant to Key Question 5: ship a same-ID `placed_feature` JSON and it wins by load order.**

**Tectonic 3.0.26** (`tectonic-3.0.26-neoforge-21.1.jar`), author Apollo (same author as Lithostitched):
- Ships its worldgen data inside an **embedded resource-pack directory, `resourcepacks/tectonic/`**, not raw `data/` at jar root — a different packaging choice from Terralith. Base pack contains `data/minecraft/worldgen/noise_settings/overworld.json` (100 KB) and ~20 `data/minecraft/worldgen/density_function/overworld/*`/`noise_router/*` files (including `temperature.json`, `vegetation.json`, and noise-router `barrier`, `continents`, `depth`, `erosion`, `final_density`, `fluid_level_floodedness`, `fluid_level_spread`, `initial_density_without_jaggedness`) plus its own `data/tectonic/worldgen/{configured_feature,placed_feature}/underground_river/*` (verified, `unzip -l`).
- **No** `multi_noise_biome_source_parameter_list` override anywhere in the jar, and no `Region`/`MNBS`-related mixin in `tectonic.mixins.json` — **Tectonic does not add or touch biome placement at all; it only reshapes terrain height/climate-adjacent density functions.** Biome-list merging (when needed) is left entirely to Lithostitched.
- **Definitive proof of the Terralith+Tectonic merge mechanism** — read from `resourcepacks/tectonic/pack.mcmeta`'s `"neoforge:overlays"` section:
  ```json
  {"directory": "overlay.terratonic", "neoforge:conditions": [{"type": "neoforge:mod_loaded", "modid": "terralith"}]}
  {"directory": "overlay.clifftree",  "neoforge:conditions": [{"type": "neoforge:mod_loaded", "modid": "mr_clifftree"}]}
  ```
  When (and only when) `neoforge:mod_loaded` reports `terralith` present, Tectonic activates `overlay.terratonic/data/minecraft/worldgen/noise_settings/overworld.json` — a **325 KB, hand-authored, combined** noise-settings file (merging Tectonic's terrain shaping with Terralith-specific density functions), instead of its own 100 KB base file. A parallel `overlay.terratonic_26_2/` (337 KB) exists specifically version-pinned for Terralith 2.6.2, and `overlay.26_2/` (also 337 KB, gated by pack-format range `[107,999]` rather than a mod-loaded condition) appears to be a related format-version-specific variant. `overlay.clifftree/` does the same pattern for a different, unrelated terrain mod ("mr_clifftree"/"Clifftree"). Other overlays (`overlay.no_carvers`, `overlay.ore_fix`, `overlay.ultrasmooth`) are gated behind Tectonic's **own** config condition (`"type": "tectonic:config"`, the same `ICondition` pattern as Terralith's `terralith:config`) — `overlay.ore_fix` specifically ships replacement vanilla `placed_feature` files (`ore_diamond`, `ore_diamond_buried/large/medium`, `ore_gold`, `ore_gold_extra`, `ore_gravel`, `ore_lapis`, `ore_lapis_buried`, `ore_redstone`, `ore_redstone_lower`, `ore_tuff`) to fix vanilla ore Y-ranges after Tectonic changes world height limits (verified, full `pack.mcmeta` read + `unzip -l`, same jar).
  - **This is a closed, pairwise compatibility model, not a generic bridge**: Tectonic ships alternate content keyed to *specific, named* mod IDs it knows about in advance (`terralith`, `mr_clifftree`). A third-party mod (e.g. a new simulation-driven generator) gets none of this automatically — Tectonic would need to ship a new overlay keyed to that mod's ID, which requires Tectonic's author to know about and support it explicitly.
- Mixins (`tectonic.mixins.json`, all in package `dev.worldgen.tectonic.mixin`, 13 total): `BiomeMixin` (`@Mixin(Biome.class)`, shifts the `BlockPos` passed into `getHeightAdjustedTemperature` by a configurable Y-offset — moves the effective snowline), `TemperatureModifierMixin` (`@Mixin(targets={"net.minecraft.world.level.biome.Biome$TemperatureModifier$2"})`, same snowline trick on the FROZEN temperature modifier), `NoiseBasedChunkGeneratorMixin` (`@Mixin(NoiseBasedChunkGenerator.class)`, injects at `<init> RETURN` to force a config-driven lava level below Tectonic's adjustable min-Y, gated on `settings.unwrapKey().map(key -> key.location().getPath().equals("overworld"))` — note this checks only the **path**, not namespace, of the noise-settings resource key), `NoisesMixin` (`@Mixin(Noises.class)`, remaps `tectonic:parameter/<name>` seed-hash lookups to `minecraft:<name>` for deterministic terrain), `ChunkDataMixin` (`@Mixin(ChunkSerializer.class)`, stores a "blending version" NBT tag to force re-blending old chunks after a height-limit config change), plus `BlendingDataMixin`, `ChunkAccessMixin`, `DimensionTypeAccessor`, `HeightmapMixin`, `IOWorkerMixin`, `NoiseSettingsAccessor`, `StructurePieceMixin`, and client-only `WorldCreationUiStateMixin` (drives a custom "Tectonic preset" selector in the world-creation screen) (all verified by decompiling the extracted classes with cfr).
- `tectonic.mixins.json`'s own `[[dependencies.tectonic]]` in `neoforge.mods.toml` lists **only `minecraft`** — no formal NeoForge dependency on Lithostitched is declared, even though Tectonic is co-developed with it by the same author and the `overlay.*`/config-condition mechanisms mirror Lithostitched/Terralith conventions closely (verified, `neoforge.mods.toml`, same jar).

**Lithostitched 1.8.0+beta4** (`lithostitched-1.8.0+beta4-neoforge-21.1.jar`), 346 classes, author Apollo:
- `neoforge.mods.toml`: `modId="lithostitched"`, depends on `minecraft [1.21,1.21.1]` and `apollib [1.2.0,)` (a shared utility library by the same author) — **no dependency on TerraBlender** (verified, same jar).
- Registers its own datapack registries (`dev.worldgen.lithostitched.api.registry.LithostitchedRegistries`, decompiled): `worldgen_modifier`, `surface_rule`, `bandlands`, `template_list`, **`biome_injector`**, `fast_noise_config`, **`region`**, plus `*_type` sub-registries for each (codec-dispatch extensibility). The presence of `region` and `biome_injector` confirms Lithostitched implements **its own, TerraBlender-independent, datapack/JSON-driven biome-region-injection system**, architecturally parallel to (not a wrapper around) TerraBlender's Java-API one.
- **Codec-level extension of vanilla classes via Mixin** (the mechanism behind the `lithostitched:biomes`/`lithostitched:migration_biome` fields seen in Terralith's file above): `MNBSPLMixin` (`@Mixin(MultiNoiseBiomeSourceParameterList.class)`) redirects the static codec-building call to add two new **optional** fields, `"lithostitched:biomes"` (an alternate `Climate.ParameterList<Holder<Biome>>`) and `"lithostitched:migration_biome"` (a sentinel `Biome`); `MNBSMixin` (`@Mixin(MultiNoiseBiomeSource.class)`) redirects its own codec-building call so that if a parameter list's *last* entry's biome equals another list's registered migration-biome sentinel, it swaps to reference the shared `MultiNoiseBiomeSourceParameterLists.OVERWORLD` registry object instead — this is how multiple mods' separately-authored `lithostitched:biomes` lists get merged into one canonical shared object at load time (both fully decompiled with cfr from the extracted `.class` files).
- **Biome injector JSON schema**, read directly from Terralith's own use of it (`data/terralith/lithostitched/biome_injector/disable_skylands_summer.json`):
  ```json
  {"type": "lithostitched:replace_fully", "dimension": "minecraft:overworld", "targets": "terralith:skylands_summer", "replacement": "minecraft:deep_lukewarm_ocean"}
  ```
  — a simple, data-driven "replace biome A with biome B, dimension-scoped" post-process, applied after the base parameter list loads (verified, `Terralith_1.21.1_v2.6.2_Neoforge.jar`).
- **TerraBlender compatibility shim** (soft/optional, no hard dependency): `dev.worldgen.lithostitched.mixin.common.compat.terrablender.NoiseBasedChunkGeneratorMixin` (`@Mixin(NoiseBasedChunkGenerator.class)`) wraps two calls inside `doCreateBiomes` (`BelowZeroRetrogen.getBiomeResolver` and `ChunkAccess.fillBiomesFromNoise`); if the resolver is Lithostitched's own internal `InjectorBiomeSource` wrapper **and** `LithostitchedPlatform.isModLoaded("terrablender")` is true, it unwraps to get TerraBlender's actual resolver as the base, applies Lithostitched's biome-injector logic around *that*, then re-wraps — meaning Lithostitched's `biome_injector` JSON system layers correctly on top of TerraBlender's own region-based resolution when both are present (fully decompiled, cfr).
- Other confirmed mixins targeting concrete vanilla classes (all in `lithostitched.mixins.json`, package `dev.worldgen.lithostitched.mixin`): `common.NoiseBasedChunkGeneratorMixin` (fixes `spawnOriginalMobs`'s biome sampling to use actual terrain height, not raw Y — relevant to tall/floating Terralith terrain), `common.bandlands.NoiseBasedChunkGeneratorMixin` (injects at `HEAD` of `buildSurface`, applies a custom striped "Bandlands" surface-color effect via the `bandlands` registry), `common.SurfaceRulesContextMixin` (`@Mixin(SurfaceRules.Context.class)`, exposes previously-private fields via a duck interface so Lithostitched's own custom `SurfaceRules.Condition`/`RuleSource` types can read chunk/noise/biome context — this is what backs the `worldgen_modifier` registry's `AddSurfaceRuleModifier`), `common.density.DensityFunctionsMapAllMixin` (`@Mixin(targets={"...DensityFunctions$Ap2","...$RangeChoice","...$ShiftedNoise","...$Spline"})`, adds a memoization cache around `mapAll` — a performance optimization, not a shape change), plus accessor/mixin classes for `NoiseChunk`, `RandomState`, `NoiseGeneratorSettings`, `BiomeGenerationSettings`, `MobSpawnSettings`, `ChunkMap`, `JigsawStructure`, `StructureTemplatePool`, and per-structure-type piece classes (`EndCity`, `Igloo`, `NetherFossil`, `OceanRuin`, `RuinedPortal`, `Shipwreck`, `WoodlandMansion`), plus `VillagerTypeMixin` (biome→villager-type mapping, matching Terralith's bundled `data/biome_tag_villagers`) (all confirmed present in `lithostitched.mixins.json`; the ones listed with mechanism detail above were fully decompiled).
- `AddSurfaceRuleModifier` (a `WorldgenModifier` registry entry, decompiled): `record AddSurfaceRuleModifier(Optional<LoadPredicate> predicate, int priority, List<ResourceKey<LevelStem>> levels, InjectionType injectionType, SurfaceRules.RuleSource surfaceRule)` — confirms surface-rule injection is **per-LevelStem-scoped** (a list of dimensions, not overworld-only), ordered by `priority`, with `InjectionType` (default `PREPEND`) controlling where in the rule tree it splices in.

### Inferences
- Because Terralith's `multi_noise_biome_source_parameter_list/overworld.json` has no plain `"biomes"` key and relies on Lithostitched's Mixin-extended codec to be meaningful, and because Terralith formally requires Lithostitched via a `required` mod dependency (which NeoForge enforces at the mod-loading level, refusing to start the instance at all if missing), the practical failure mode if Lithostitched's classes/mixins ever became unavailable (e.g. an option (ii) generator that somehow prevented Lithostitched's own mixins from applying) is not "Terralith's biomes silently disappear" but "the modpack fails to load" or "the file parses to something degenerate" — this is a much harder failure than a quietly-inert mixin.
- Given that **both** Terralith and Tectonic ship literal same-ID `data/minecraft/worldgen/noise_settings/overworld.json` and multiple same-ID `density_function/overworld/*` files, and vanilla/NeoForge datapack JSON resources do not deep-merge (one pack's file wins outright per resource ID, by pack load-order), a third mod adding a *third* same-ID override (as a simulation-driven option (i) generator plausibly would, to inject its own noise-router inputs) would collide the same way — the resolution Tectonic and Terralith actually use for each other (bespoke hand-merged `overlay.terratonic*` files, gated on knowing the other mod's exact ID) is not something a new, unknown mod can obtain automatically; it would need equivalent bespoke authoring on someone's part, or the new mod would need to avoid the same file IDs entirely and instead work by patching/wrapping already-loaded density functions in Java (mirroring Lithostitched's own approach).

### Gaps
- The exact call site where `AddSurfaceRuleModifier.apply(RegistryAccess)` gets invoked was not fully confirmed — the decompiled method body appeared empty (`public void apply(RegistryAccess registries) { }`), which may be a `cfr` limitation on this specific record given the "could not load" warnings for several referenced classes, or the real application logic may live in a separate dispatcher class (e.g. tied to `RegistryDataLoaderMixin` or `NoiseGeneratorSettingsAccessor`) that was not individually decompiled. The JSON schema (predicate/priority/levels/injection_type/surface_rule fields) is solid; the precise Java call path that consumes it is not.
- The exact precedence/resolution mechanism between Tectonic's base `resourcepacks/tectonic/` pack and Terralith's raw `data/` (when Terralith is present but, hypothetically, an `overlay.terratonic` condition fails to match for some reason) was not empirically tested — no game launch was performed per constraints.
- Whether `overlay.26_2` (format-range-gated, not mod-ID-gated) is Terralith-version-specific or purely a Minecraft-pack-format compatibility shim was not fully disambiguated from static inspection alone.

## Key question 4 — Other fantasy/unusual overworld terrain: categorized mechanisms and survival under option (i)/(ii)

### Takeaway
Across a floating-island datapack pattern, Alex's Caves, Deeper and Darker, YUNG's mod family, and The Aether, **every mod that stays inside the Overworld uses either category (2) density-function overrides on the same vanilla resource IDs, or category (6) mixins into the concrete `MultiNoiseBiomeSource`/`ChunkGenerator` classes — both of which are exactly the same two mechanism families already documented for TerraBlender and Lithostitched.** Mods that instead ship a wholly **separate dimension** (Deeper and Darker's "Otherside", The Aether) turn out to need **no bespoke Java `ChunkGenerator` at all** — both are built on vanilla's own generic, data-driven `minecraft:noise` generator + `minecraft:multi_noise` biome source, just pointed at their own dimension key, noise-settings ID, and biome list; this makes them completely unaffected by either option (i) or (ii), since they never touch whatever generator ends up serving the Overworld.

### Cited Findings — per mechanism, with option (i)/(ii) verdicts

**(A) Floating-island terrain via standalone datapack** — mechanism = category (2), datapack-only, no mod code.
- Youmiel/FloatingIslands-Datapack: a pure datapack (no mixin, no code) spanning MC 1.16.x–1.21.9 across version branches, working by overriding Overworld (and Nether) density functions/noise settings directly and scattering End Gateways as placed features. [Source](https://github.com/Youmiel/FloatingIslands-Datapack)
- Multiple independent authors converged on the identical pattern: "Islands Overworld [1.21]" [Source](https://www.planetminecraft.com/data-pack/islands-overworld/), "Revamped Floating Islands" [Source](https://modrinth.com/datapack/revamped-floating-islands), "Aetherial Islands" [Source](https://modrinth.com/datapack/aetherial-islands), "End-like Floating Islands" (explicitly lists 1.21.1) [Source](https://modrinth.com/datapack/end-like-floating-islands). Mod-based variants exist too: "Rob's Floating Islands" for NeoForge 1.21.1. [Source](https://modrinth.com/mod/robs-floating-islands)
- **Survives (i)?** Conditional/collision risk — these datapacks overwrite the exact same `worldgen/density_function/*`/`worldgen/noise_settings/overworld.json` resource IDs an option-(i) simulation-driven generator would also need to control; two same-ID overrides do not merge, whichever loads last wins outright. **Survives (ii)?** No, unless the custom generator specifically still parses vanilla `noise_settings`/`density_function` datapack JSON — a bespoke procedural generator with no density-function interpreter gives such a datapack nothing to hook into.

**(B) Alex's Caves** (AlexModGuy/sbom_xela) — mechanism = category (6) primarily (mixin into `MultiNoiseBiomeSource`), plus category (3)/(4).
- Source repo confirmed at [Source](https://github.com/AlexModGuy/AlexsCaves); a `1.21.1` branch exists in source control, but **no public 1.21.1 release was found on Modrinth or CurseForge as of 2026-09-27** — the latest shipped version is 2.0.2 for MC 1.20.1 only (Forge/NeoForge), confirmed independently via both a direct Modrinth version-list fetch and a separate sub-agent check. Treat "Alex's Caves on 1.21.1" as an in-progress source branch, not a released mod, as of this research date.
- Its datapack side (`data/alexscaves/worldgen/`) has only `biome`, `configured_feature`, `placed_feature`, `structure`, `structure_set` — no `density_function`/`noise_settings` anywhere, and it does not override vanilla's `multi_noise_biome_source_parameter_list`.
- Instead, `MultiNoiseBiomeSourceMixin` (`@Mixin(value = MultiNoiseBiomeSource.class, priority = -69420)`) injects at `HEAD` of `getNoiseBiome(int,int,int,Climate.Sampler)`, cancellable — it can short-circuit vanilla's own biome lookup and substitute its own result, achieving a category-1-like *outcome* (new biomes appear in the normal chunk grid) via a category-6 *mechanism* (intercepting the method, not adding parameter points vanilla's own search would merge). A companion `BiomeSourceMixin` (`@Mixin(BiomeSource.class)`) exposes accessor methods so the injected biomes register as legitimate outputs (e.g. for `/locate biome`). [Source](https://raw.githubusercontent.com/AlexModGuy/AlexsCaves/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/mixin/MultiNoiseBiomeSourceMixin.java) / [Source](https://raw.githubusercontent.com/AlexModGuy/AlexsCaves/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/mixin/BiomeSourceMixin.java)
- Access is gated behind an "Underground Cabin" structure + item/quest chain (cave tablet → Cave Compendium → cave codex → biome map) — category (4).
- A GitHub issue reports cave biomes failing to generate "if you exceed 365 MODS," with no root-cause discussion — consistent with, but not confirmed as, a multi-noise/mixin-ordering conflict. [Source](https://github.com/AlexModGuy/AlexsCaves/issues/141)
- **Survives (i)?** Yes, mechanically — the mixin fires on `MultiNoiseBiomeSource.getNoiseBiome`, which still exists and runs under option (i); caveat that if its internal trigger logic reads specific vanilla noise-router value ranges, a simulation with a different value distribution could shift where/how often its biomes appear. **Survives (ii)?** No — the mixin targets the *concrete* `MultiNoiseBiomeSource` class; a fully custom `BiomeSource` under option (ii) that doesn't instantiate that class never calls `getNoiseBiome` on it, so the hook becomes dead code (silently inert, not a crash).

**(C) Deeper and Darker** (KyaniteMods) — mechanism = category (5), built on vanilla's generic generator types.
- The real, current repository is `KyaniteMods/DeeperAndDarker` (branches `neoforge-1.21`, `neoforge-26.1` confirmed to exist) — note a Modrinth/web search for "deeper and darker" can also surface an unrelated, defunct 1.12.2 "Deeper Darker" project targeting the old Extra Utilities 2 dimension; that is a different mod and was excluded here. [Source](https://github.com/KyaniteMods/DeeperAndDarker)
- Its generated dimension file, `data/deeperdarker/dimension/otherside.json`, defines a custom `DimensionType` `deeperdarker:otherside` with `"generator": {"type": "minecraft:noise", "biome_source": {"type": "minecraft:multi_noise", "biomes": [4 biomes: Deeplands, Echoing Forest, Overcast Columns, Blooming Caverns]}, "settings": "deeperdarker:otherside"}` — this reuses vanilla's generic, data-driven noise generator and multi-noise biome source wholesale; **no bespoke Java `ChunkGenerator` subclass is needed.** [Source](https://raw.githubusercontent.com/KyaniteMods/DeeperAndDarker/neoforge-1.21/src/generated/resources/data/deeperdarker/dimension/otherside.json)
- The only vanilla-namespace touch found is a `data/minecraft/structure` addition consistent with placing the Otherside's entry portal inside the vanilla Ancient City structure (accessed via "the center portal in Ancient Cities"). [Source](https://github.com/KyaniteMods/DeeperAndDarker/wiki/The-Otherside)
- Confirmed live for 1.21.1 NeoForge: Modrinth version `1.4.1-neoforge-1.21.1` (2026-06-05). [Source](https://modrinth.com/mod/deeperdarker)
- **Survives (i) and (ii)?** Yes, both — `otherside` is a fully separate dimension key with its own generator/biome-source instance and noise settings, decoupled from whatever serves the Overworld under either option. Second-order risk (not a mechanism failure, but worth flagging): its only entry point is a portal inside a vanilla Ancient City — if an option (ii) generator skips Minecraft's normal structure-placement pipeline, the Ancient City (and thus the portal) might not generate, indirectly cutting off access even though the Otherside dimension itself is untouched.

**(D) YUNG's mods** — structure mods = category (4); Better Caves = carver-based (a variant of category 2).
- Confirmed live on 1.21.1 NeoForge (version numbers via Modrinth): Better Caves v3.1.6, Better Mineshafts v5.1.1, Better Strongholds v5.1.3, Better Dungeons v5.1.4, Better Desert Temples v4.1.5, Better Ocean Monuments v4.1.2; Better Nether Fortresses, Better Jungle Temples, Better Witch Huts, Better End Island also exist as current separate repos under the YUNG-GANG GitHub org. [Source](https://github.com/YUNG-GANG) "YUNG's Better Structures" is not an actual current standalone product — no such repo/listing was found; the real current products are the individually-named mods above.
- The structure mods are jigsaw/structure-template replacements riding the normal structure-placement pipeline — category (4).
- YUNG's Better Caves instead works through vanilla's **`WorldCarver`/carver system** — configurable custom carvers built explicitly on "the vanilla `minecraft:cave` carver type," using pluggable noise types (Value/Perlin/Simplex/Cellular/Cubic and Fractal variants). [Source](https://github.com/yungnickyoung/YUNGs-Better-Caves/wiki/1.20.1-%26-1.21.1-Configuration-Guide) Carvers are a **separate, older pipeline step** (`ChunkGenerator.applyCarvers()`) from the density-function noise-router system that shapes 1.18+ terrain, and this step still runs inside `NoiseBasedChunkGenerator` after initial density-function shaping — closest fit is category (2), but carver-based specifically, not density-function-based.
- **Survives (i)?** Likely yes for both: structure placement doesn't consume noise-router climate outputs directly (though biome-tag-gated spawn conditions must still resolve against whatever biomes a simulation-fed `MultiNoiseBiomeSource` produces); carvers run their own pipeline step using mostly their own noise + biome tags, largely independent of specific climate-parameter values. **Survives (ii)?** Depends entirely on whether the custom `ChunkGenerator` still invokes vanilla's standard structure-placement step and `applyCarvers()` at all — a from-scratch reimplementation that omits either step breaks the corresponding YUNG's mods outright. This is a concrete design requirement to flag for any option-(ii) generator, not a hypothetical risk.

**(E) The Aether** (The-Aether-Team) — mechanism = category (5), also built on vanilla's generic generator types.
- Source confirmed at branch `1.21.1-develop` (a newer `1.21.3-develop` branch also exists). [Source](https://github.com/The-Aether-Team/The-Aether)
- `data/aether/dimension/the_aether.json`: `"type": "aether:the_aether"`, `"generator": {"type": "minecraft:noise", "biome_source": {"type": "minecraft:multi_noise", "biomes": [13 parameter-point entries across 4 biomes: skyroot_meadow/forest/grove/woodland]}, "settings": "aether:skylands"}`. [Source](https://raw.githubusercontent.com/The-Aether-Team/The-Aether/1.21.1-develop/src/generated/resources/data/aether/dimension/the_aether.json) **Correction to the task's premise:** The Aether is indeed a fully separate dimension (own `DimensionType`, own biome parameter list, disjoint from the Overworld), but it does **not** need a bespoke Java `ChunkGenerator` — like Deeper and Darker, it is built entirely on vanilla's generic `minecraft:noise`+`minecraft:multi_noise` types, just pointed at its own `aether:skylands` noise-settings ID (presumably containing the density-function graph producing its floating-island shape, using the same general density-function technique as (A) above but scoped to a private dimension).
- Confirmed live for 1.21.1 NeoForge (multiple Modrinth versions, e.g. `1.21.1-1.5.10-neoforge`); the project's newest supported MC version is 1.21.1 as of this research date, with development progressing on a `1.21.3-develop` branch. [Source](https://modrinth.com/mod/aether)
- **Survives (i) and (ii)?** Yes, both — same reasoning as (C): a wholly separate dimension key/generator/biome-list, never touching the Overworld's generator under either option.

### Inferences
- A clean pattern emerges across (C) and (E): **"separate dimension" as a mechanism category does not by itself imply custom Java worldgen code** — both real-world examples checked reuse vanilla's own generic `minecraft:noise` `ChunkGenerator` type and `minecraft:multi_noise` `BiomeSource` type, just with different registry IDs. This means a simulation-driven generator that replaces the Overworld's `ChunkGenerator`/`BiomeSource` (option ii) has **zero effect** on this entire category of mod, regardless of how the replacement is implemented — these mods were never coupled to whatever the Overworld uses in the first place.
- Every Overworld-integrated fantasy-terrain mechanism found across Key Questions 1, 2, and 4 reduces to the same two failure-prone hook types already established for TerraBlender/Lithostitched: (a) same-resource-ID datapack file replacement (collides under option i if the simulation generator also claims those IDs; inert under option ii if the custom generator doesn't read that registry at all) and (b) Mixin into the concrete `MultiNoiseBiomeSource`/`NoiseBasedChunkGenerator`/`ChunkGenerator` classes (preserved under option i; silently inert under option ii unless the replacement subclasses or wraps those same concrete classes). No third mechanism for Overworld-integrated content was found anywhere in this research.

### Gaps
- Alex's Caves' other mixin files (`JigsawStructureMixin`, `OceanMonumentStructureMixin`, `ShipwreckStructureMixin`, `SwampHutPieceMixin`, `ChunkStatusMixin`) were confirmed to exist by filename only; their exact `@Mixin` targets/behavior were not read.
- The Aether's `aether:skylands` noise-settings file itself (which would show the actual floating-island density-function graph) was not fetched — only the dimension file referencing it by ID was verified, so the specific density-function technique used is inferred by analogy to (A)/Terralith's Skylands, not directly confirmed for the Aether.
- Youmiel/FloatingIslands-Datapack's claimed 1.16.x–1.21.9 version range is taken from its README; no specific 1.21.1 release tag was independently opened.
- No standalone floating-island/sky-terrain mod or datapack that is both (a) confirmed released for 1.21.1 NeoForge specifically and (b) independently source-verified (rather than description-only) was found — this entire category rests on descriptions/READMEs more than on direct code reads, unlike TerraBlender/Lithostitched/Terralith/Alex's Caves/Deeper and Darker/Aether above.

## Key question 5 — Ores and stone: vanilla mechanics, NeoForge tags/modifiers, ore-variant mods, Create, Geolosys/GregTech, Create Ore Excavation

### Takeaway
Vanilla ore placement is ordinary configured/placed features gated by `rule_test` against `#minecraft:stone_ore_replaceables`/`#minecraft:deepslate_ore_replaceables`; vanilla's *large ore veins* are a **separate, older-pipeline mechanism** — a `NoiseChunk.BlockStateFiller` (`OreVeinifier`) wired directly into terrain shaping from three literal fields (`veinToggle`/`veinRidged`/`veinGap`) of the `NoiseRouter` record, not a placed feature and not (in stock vanilla) named density-function registry entries. NeoForge's `neoforge:add_features`/`remove_features` biome modifiers and a rich `c:ores`/`c:ores/<material>`/`c:ores_in_ground/<stone>`/`c:raw_materials`/`c:storage_blocks` convention-tag family are all confirmed present with exact names from NeoForge 21.1.249 source. Create Ore Excavation (in the MIC pack) uses **zero vanilla worldgen registries** — its veins are custom recipe JSON resolved by per-chunk Java logic and persisted as NeoForge data attachments, not real placed ore blocks. Of the named ore-variant/overhaul mods, only **Excavated Variants** and **GregTech CEu Modern** are confirmed alive on 1.21.1 NeoForge; **Geolosys is confirmed dead beyond 1.20.1 Forge-only**, and "Unearthed" is ambiguous (no candidate project has a confirmed 1.21.1 build). Create's palette stones (Scoria, Crimsite, Veridium, Ochrum, Scorchia) have a genuine first-class worldgen presence via the same vanilla ore-replacement tags, but generate decorative rock patches, not metal ore.

### Cited Findings

**Vanilla ore mechanics** (verified in `neoforge-21.1.249-sources.jar`, which includes mapped vanilla source, plus the `misode/mcmeta` 1.21.1-data GitHub mirror for datapack JSON cross-checks):
- `OreConfiguration` fields: `targetStates: List<TargetBlockState>` (JSON `"targets"`), `size: int` (0–64), `discardChanceOnAirExposure: float` (0–1); a tag-based target is `{"predicate_type": "minecraft:tag_match", "tag": "minecraft:stone_ore_replaceables"}`.
- Exact current tag membership (fetched from `misode/mcmeta`, branch `1.21.1-data`): `minecraft:stone_ore_replaceables = [minecraft:stone, minecraft:granite, minecraft:diorite, minecraft:andesite]`; `minecraft:deepslate_ore_replaceables = [minecraft:deepslate, minecraft:tuff]` (tuff is in the *deepslate* tag, not the stone one — a plain web-search summary reportedly got this backwards; the direct file fetch is authoritative here). [Source](https://raw.githubusercontent.com/misode/mcmeta/1.21.1-data/data/minecraft/tags/block/stone_ore_replaceables.json) / [Source](https://raw.githubusercontent.com/misode/mcmeta/1.21.1-data/data/minecraft/tags/block/deepslate_ore_replaceables.json)
- **Large ore veins are not placed/configured features and (in stock vanilla) are not named density-function registry files.** `NoiseRouter` is a `record` whose fields literally include `DensityFunction veinToggle, veinRidged, veinGap` (JSON codec names `"vein_toggle"`/`"vein_ridged"`/`"vein_gap"` inside `noise_settings/overworld.json`'s inline `"noise_router"` object) — bottoming out in noise *parameters* `minecraft:ore_veininess`/`ore_vein_a`/`ore_vein_b`/`ore_gap` (registry `worldgen/noise/`, confirmed present at that path), not `worldgen/density_function/`. `OreVeinifier` (full source read) is wired directly into terrain shaping: `NoiseChunk.java` — `builder.add(OreVeinifier.create(noiserouter1.veinToggle(), noiserouter1.veinRidged(), noiserouter1.veinGap(), random.oreRandom()))`. Exact constants from source: `veinToggle > 0` → Copper vein (`COPPER_ORE`/`RAW_COPPER_BLOCK`, filler `GRANITE`, Y 0–50) else Iron vein (`DEEPSLATE_IRON_ORE`/`RAW_IRON_BLOCK`, filler `TUFF`, Y −60..−8); `VEININESS_THRESHOLD=0.4`, `VEIN_SOLIDNESS=0.7` (≈30% early-exit chance), `MIN_RICHNESS=0.1`, `MAX_RICHNESS=0.3`, `CHANCE_OF_RAW_ORE_BLOCK=0.02`. Corroborated by the Minecraft Wiki: "Ore veins are a part of cave generation and are not decorators... they can generate in the Void biome." [Source](https://minecraft.wiki/w/Ore_vein) `ore_gold_extra` (checked directly as a candidate "consumer" of vein noise) is in fact an unrelated, older biome-gated placed feature (extra badlands gold) with no connection to the vein system.
  - **Reconciling note:** Terralith's own replacement `overworld.json` (Key Question 2) *does* factor its own vein-related sub-trees out into named registry files at `data/minecraft/worldgen/density_function/overworld/noise_router/vein_toggle.json` etc. — this is Terralith's own authoring/refactoring choice when it replaces the noise settings wholesale, not evidence that stock vanilla organizes its vein density functions that way.

**NeoForge biome modifiers** (verified in `net/neoforged/neoforge/common/world/BiomeModifiers.java` and `BiomeModifier.java`, `neoforge-21.1.249-sources.jar`):
- `AddFeaturesBiomeModifier`: `record AddFeaturesBiomeModifier(HolderSet<Biome> biomes, HolderSet<PlacedFeature> features, GenerationStep.Decoration step)`, type string **`neoforge:add_features`**. Exact JSON shape (from the class's own doc comment):
  ```json
  {"type": "neoforge:add_features", "biomes": "#namespace:your_biome_tag", "features": "namespace:your_feature", "step": "underground_ores"}
  ```
  `biomes`/`features` accept a single id, a list, or a `#tag`; `step` is a `GenerationStep.Decoration` enum name (the doc comment's own example is literally `"underground_ores"`).
- `RemoveFeaturesBiomeModifier`: `record RemoveFeaturesBiomeModifier(HolderSet<Biome> biomes, HolderSet<PlacedFeature> features, Set<Decoration> steps)`, type string **`neoforge:remove_features`** (note: plural `steps`, defaults to all steps via `allSteps(...)` if omitted).
- `BiomeModifier.DIRECT_CODEC` dispatches on `NeoForgeRegistries.BIOME_MODIFIER_SERIALIZERS`; a modifier can be disabled in a datapack by overriding its file with `{"type": "neoforge:none"}`; `Phase` enum = `BEFORE_EVERYTHING, ADD, REMOVE, MODIFY, AFTER_EVERYTHING`.
- Sibling modifier types also confirmed present in the same file: `neoforge:add_spawns`/`remove_spawns`, `neoforge:add_carvers`/`remove_carvers`, `neoforge:add_spawn_costs`/`remove_spawn_costs` — `add_carvers`/`remove_carvers` are directly relevant to suppressing/adding cave-carver-based terrain mods (e.g. YUNG's Better Caves, Key Question 4D) via the same first-party mechanism.
- Real-world confirmation: Create's own 1.21.1 generated data ships exactly this shape at `data/create/neoforge/biome_modifier/striated_ores_overworld.json`: `{"type": "neoforge:add_features", "biomes": "#minecraft:is_overworld", "features": "create:striated_ores_overworld", "step": "underground_ores"}`.

**NeoForge convention tags** (verified in `net/neoforged/neoforge/common/Tags.java`, 1390 lines, `neoforge-21.1.249-sources.jar`; real namespace confirmed as `c:` via the file's own `tag(name)` helper):
- `c:ores`, and per-material `c:ores/{coal,copper,diamond,emerald,gold,iron,lapis,netherite_scrap,quartz,redstone}` (both Block and Item tags).
- `c:ores_in_ground/{deepslate,netherrack,stone}` — tags **the ore block itself** (e.g. deepslate-hosted ore variants).
- `c:ore_bearing_ground/{deepslate,netherrack,stone}` — the reverse: tags **the replaceable host rock** (the NeoForge-convention analog of vanilla's `stone_ore_replaceables`/`deepslate_ore_replaceables`, but a distinct `c:` family; the source javadoc explicitly cross-references the two families as a pair).
- `c:ore_rates/{dense,singular,sparse}` — categorizes average ore yield (javadoc examples: dense=Copper Ore, singular=Iron Ore, sparse=Nether Gold Ore).
- `c:storage_blocks` + per-material (`bone_meal, coal, copper, diamond, dried_kelp, emerald, gold, iron, lapis, netherite, raw_copper, raw_gold, raw_iron, redstone, slime, wheat`).
- `c:raw_materials` + `/copper, /gold, /iron` **only** — Item tag only, no Block-tag equivalent (raw-ore-block form lives under `c:storage_blocks/raw_iron` etc. instead).
- `c:dusts` + `/redstone, /glowstone` **only** — Item only, no generic per-metal dust family (no `dusts/iron`, `dusts/copper`, etc. shipped by NeoForge itself).
- `c:ingots` + `/copper, /gold, /iron, /netherite` — Item only (no diamond ingot, correctly, since diamond isn't an ingot); `c:nuggets` + `/gold, /iron`.
- **Confirmed NOT present** anywhere in NeoForge's own `Tags.java` (exhaustive grep): `c:ores/tin`, `/silver`, `/lead`, `/nickel`, `/zinc`; `c:raw_materials/netherite`, `/diamond`; `c:dusts/iron`, `/copper`, `/gold`; `c:ingots/diamond`. Any mod using tags like these is applying its own or a different cross-mod convention, not something NeoForge itself defines — do not assume such tags exist without checking that specific mod.

**Create Ore Excavation** (`createoreexcavation-1.21-1.6.8.jar`, modid `createoreexcavation`, in the MIC pack's mods folder):
- **Uses zero vanilla worldgen registries.** Full jar listing (357 files) contains no occurrence of the string `worldgen` anywhere — no `configured_feature`, `placed_feature`, `biome_modifier`, or `density_function` under either its own or the `minecraft:` namespace.
- Vein "types" are custom **recipe JSON** (`"type": "createoreexcavation:vein"`) at `data/createoreexcavation/recipe/ore_vein_type/{iron,copper,diamond,coal,emerald,glowstone,gold,hardened_diamond,lapis,netherite,nether_gold,quartz,redstone,water,zinc}.json`. Example (`iron.json`):
  ```json
  {"type":"createoreexcavation:vein","amountMultiplierMax":30.0,"amountMultiplierMin":10.0,"biomeWhitelist":"minecraft:is_overworld","finite":"default","icon":{"count":1,"id":"minecraft:raw_iron"},"placement":{"salt":1544847576,"separation":8,"spacing":128},"priority":0}
  ```
  Biome/dimension binding is via `biomeWhitelist` using vanilla biome tags (`minecraft:is_overworld` for iron/copper/diamond/water; `minecraft:is_nether` for nether_gold/glowstone) — a biome predicate, not a literal dimension field, that happens to partition along dimension lines.
- `"placement": {salt, separation, spacing}` mirrors vanilla's `RandomSpreadStructurePlacement` fields; the mod ships its own `com/tom/createores/util/RandomSpreadGenerator.class` reimplementing that grid-jitter algorithm, and `com/tom/createores/OreVeinGenerator.class` resolves a `LevelChunk → RecipeHolder<VeinRecipe>` per chunk (confirmed via `javap` constant-pool inspection).
- **Persistence is via NeoForge Data Attachments, not real placed ore blocks**: `CreateOreExcavation.class` builds a `net.neoforged.neoforge.attachment.AttachmentType<OreDataAttachment>`; `OreDataAttachment.class` implements `INBTSerializable<CompoundTag>` with its own `Codec` — vein state is stored as per-chunk/level attached NBT, not written into terrain. Consistent with lang-file text describing a "Vein Finder" that locates a vein "Found in Chunk" and a stationary drill that "extract[s] the results" over time, with no block-breaking language.

**Ore-variant/overhaul mod status on 1.21.1 NeoForge** (checked 2026-09-27, Modrinth API primarily, one CurseForge cross-check):
- **Excavated Variants** (slug `excavated_variants`): confirmed NeoForge build for 1.21.1, version 4.3.1 (2024-08-13). Its own project description: it "generates real new ore blocks... for each combination of ore and stone variant" and "attempts to set up world gen for these ore variants" — a real dynamic ore-block generator (patches placement so a stone-matched ore variant spawns adjacent to its matching stone), not a texture reskin. Ships default compat configs for a list including Create and "Unearthed."
- **"Unearthed"** — ambiguous, two independently verified findings conflict/don't resolve cleanly: (a) my own quick Modrinth search surfaced `unearthed-unofficial-port` ("Configurable underground stone/ore generation & more stone types! Better caves & cliffs!") and `unearthed-cainthetrain` ("A mod adding new ores and metals to the game"); (b) a deeper sub-agent check found `unearthed-cainthetrain`'s published `game_versions` are only `1.21.4` and `1.21.8` — **no 1.21.1 build**, and its mechanic (wholly new ore/metal types) differs from "dynamic per-stone-type variants of existing ores." Neither candidate is confirmed to have a 1.21.1 NeoForge release; which mod the task intended is not resolved.
- **Geolosys** — **confirmed dead beyond 1.20.1, Forge-only**, cross-checked two independent ways: my own direct Modrinth project fetch (`game_versions` topping out at `1.20.1`, `loaders: ["forge"]` only) and a separate sub-agent's CurseForge + Modrinth cross-check (latest CurseForge file "Geolosys 1.20.1 7.0.14," Jul 2025; a community continuation `geolosys-next` reaches MC 1.20.6 but is also Forge-only). No Fabric or NeoForge port exists under any name/spelling checked.
- **GregTech CEu Modern** — **confirmed available for NeoForge 1.21.1**, cross-checked two independent ways (my own direct fetch and a sub-agent fetch agree exactly): Modrinth slug `gregtechceu-modern`, latest 1.21.1/NeoForge build `mc1.21.1-7.0.2` (2025-07-20). Important nuance: this is not the project's overall latest release — the single most recent release across the whole project is `mc1.20.1-7.5.3` (Forge, 1.20.1-only, 2026-04-12) — the 1.21.1/NeoForge line is roughly 9 months behind the actively-developed 1.20.1/Forge line as of 2026-09-27. (Note: earlier in this research, a lookup under the guessed slug `gtceu` returned HTTP 404 — the correct slug is `gregtechceu-modern`; don't assume `gtceu` resolves.)
- **Create (base mod) palette stones have a real, first-class worldgen role — but it's decorative rock generation, not ore generation.** Verified directly from `Creators-of-Create/Create` GitHub, branch `mc1.21.1/dev` (Create 6.0.10 for MC 1.21.1, current NeoForge release, published 2026-04-21): `src/main/java/com/simibubi/create/infrastructure/worldgen/` still ships `AllBiomeModifiers`, `AllConfiguredFeatures`, `AllFeatures`, `AllPlacedFeatures`, `AllPlacementModifiers`, `LayeredOreConfiguration`, `LayeredOreFeature`. Accurate characterization: Create's palette stones generate as decorative rock-formation patches using vanilla's exact ore-replacement machinery; Create's only actual new metal-ore worldgen is `zinc_ore` — iron/copper/gold etc. used by Create's own recipes remain 100% vanilla-sourced.

### Inferences
- Because ore suppression/addition in both vanilla and Create is uniformly expressed as `rule_test`-against-tag configured features plus `neoforge:add_features`/`remove_features` biome modifiers, a simulation-driven world generator wanting to suppress or override any given mod's ore features has a clean, first-party, already-proven mechanism available regardless of option (i) or (ii): ship a datapack `neoforge:remove_features` modifier (or a same-ID `placed_feature`/`configured_feature` override, as Terralith ReStoned does for vanilla's own stone-blob features) targeting the specific `PlacedFeature`s to remove. This mechanism is independent of which `ChunkGenerator`/`BiomeSource` classes are in use, since biome modifiers operate on `BiomeGenerationSettings` (populated once per biome, before/independent of chunk generation) rather than on the generator itself — **this is the one ore/stone mechanism in this whole research task that appears equally robust under both option (i) and option (ii)**, unlike almost everything else investigated, which is graded by concrete-class survival.
- Create Ore Excavation's complete independence from vanilla worldgen registries (pure recipe-JSON + Java + data-attachment persistence) means it is **automatically compatible with either option (i) or option (ii)** — it never reads `NoiseGeneratorSettings`, `MultiNoiseBiomeSource`, or any density function; its only touchpoint with the world is the biome tag on `biomeWhitelist` and ordinary chunk load/save hooks, both of which are generator-agnostic.
- GregTech CEu Modern's ore-vein generation mechanism itself (historically a large, proprietary "vein/deposit" system distinct from vanilla ore features in older GregTech versions) was not verified for the current 1.21.1 port — given it's confirmed alive but trailing the mod's actively-developed branch by many releases, and given how large/complex GregTech's worldgen has historically been, this is flagged as a priority follow-up if GregTech compatibility specifically matters to the target pack.

### Gaps
- The exact numeric/algorithmic behavior of Create Ore Excavation's vein selection and yield calculation (how `salt`/`spacing`/`separation`/`priority`/`amountMultiplier`/`finite` combine) was not verified — only field/class-name/constant-pool evidence was available; method bodies were not decompiled for this mod.
- Whether the vanilla tag names `stone_ore_replaceables`/`deepslate_ore_replaceables` were ever spelled differently in an older Minecraft version was not chased (only the current 1.21.1 name was confirmed).
- GregTech CEu Modern's actual ore-vein/deposit generation mechanism (as opposed to its version availability) was not researched.
- Which specific mod the task's "Unearthed" reference is meant to identify remains unresolved; neither Modrinth candidate is confirmed to ship for 1.21.1.
- `create:cinder`'s worldgen participation (if any) was not found in the two worldgen JSON files checked and was not chased further.

## Key question 6 — World presets (Large Biomes / Amplified / custom) and compat libraries bridging custom chunk generators to TerraBlender

### Takeaway
**Sources conflict and are presented separately rather than resolved by guessing.** Direct file-level inspection of the actual Terralith 2.6.2 and Tectonic 3.0.26 jars shows **neither ships any override for `worldgen/noise_settings/large_biomes.json` or `amplified.json`** — only `overworld.json` is touched. Separately, Terralith's own Modrinth listing claims full Large Biomes/Amplified/Single Biome/Superflat support "as of 2.6.0," attributed to a fixed vanilla engine bug (MC-260949). Both are individually well-sourced; a plausible (but unverified) reconciliation is given in Inferences. Tectonic and Biomes O' Plenty have **no discoverable statement at all** about non-default presets. No dedicated third-party mod exists whose specific purpose is bridging an arbitrary custom `ChunkGenerator` to TerraBlender — **TerraBlender is its own bridge**, and Lithostitched is a separate, parallel bridging layer for its own dependent mods (with an optional soft-compat shim for TerraBlender specifically, Key Question 2).

### Cited Findings
- **Direct evidence (this research, not web-sourced):** neither `Terralith_1.21.1_v2.6.2_Neoforge.jar` nor `tectonic-3.0.26-neoforge-21.1.jar` contains any file matching `worldgen/noise_settings/{large_biomes,amplified}.json` (verified via `unzip -l` grep against both jars).
- **Vanilla cross-check (this research):** fetched vanilla's actual `data/minecraft/worldgen/noise_settings/large_biomes.json` and `amplified.json` from the local `neoforge-21.1.249-client-extra-aka-minecraft-resources.jar`. Both reference several `minecraft:overworld/...`-namespaced shared density functions: `large_biomes.json` references `overworld/caves/{entrances,noodle,pillars,spaghetti_,spaghetti_roughness_function}` and `overworld/ridges`; `amplified.json` references the same cave set plus `overworld/continents` and `overworld/erosion`. Since Terralith directly overrides `data/minecraft/worldgen/density_function/overworld/caves/entrances.json`, `.../caves/pillars.json`, and `noise_router/{erosion,ridges}.json` at those exact shared IDs (Key Question 2), **selecting Large Biomes or Amplified would still partially inherit Terralith's cave-entrance/pillar and ridge (and, for Amplified, continentalness/erosion) density-function edits, while getting none of Terralith's ~100 custom biomes or its other terrain features** (which live in `terralith:`-namespaced files only reachable from Terralith's own `overworld.json`, not from `large_biomes.json`/`amplified.json`) — a hybrid, almost certainly unintended result, not a clean fallback to vanilla and not a clean Terralith experience `(verified by direct grep of both vanilla noise-settings files, local jar)`.
- **Terralith's own compatibility claim (web-sourced, in tension with the above):** "As of 2.6.0, the mod version of Terralith adds support for all world types... will respect superflat worlds, and work with the Single Biome, Large Biomes, and Amplified world types," plus two custom presets of its own, `terralith:amplified_large_biomes` and `terralith:all_skylands`. [Source](https://modrinth.com/mod/terralith) The stated root cause: "Due to this Minecraft bug (MC-260949), worldgen datapacks cannot support other world types, such as Large Biomes, Amplified, or Superflat" — described as an engine bug fixed in the *mod* version of Terralith as of 2.6.0, "not backported to earlier Minecraft versions." [Source](https://github.com/Stardust-Labs-MC/Terralith/issues/113) The same page also states: "Terralith is compatible with most biome-adding mods when using Terrablender or equivalent, but biome-adding datapacks are typically not compatible," and the wiki adds: "Being an Overworld WorldGen project, other WorldGen Datapack/Mods for the Overworld that add biomes will likely not work well alongside Terralith unless compatibility was brought by either side through an addon or update." [Source](https://stardustlabs.miraheze.org/wiki/Terralith_compatibilities)
- **Tectonic** — no statement on Large Biomes/Amplified/custom presets was found anywhere checked (Modrinth description, GitHub README, GitHub wiki). Its Modrinth "Biome Mod Compatibility" section discusses TerraBlender/Biolith-based mods, a dedicated Terralith compatibility patch (the "Terratonic" datapack, Key Question 2), and "CliffTree" — but nothing about world presets. [Source](https://modrinth.com/mod/tectonic) Its GitHub wiki's "General FAQ" and "Terratonic FAQ" pages returned load errors on every fetch attempt and their content is unverified, not confirmed absent. A closed, unanswered GitHub issue (#222) reports that manually editing `xz_scale` in Tectonic's density functions "doesn't seem to have any effect" when Tectonic runs alongside Terralith — an unresolved user report, not documented behavior. [Source](https://github.com/Apollounknowndev/tectonic/issues/222)
- **Biomes O' Plenty** — no statement found on Large Biomes/Amplified/custom-preset compatibility in its CurseForge page, Modrinth description, or wiki.gg homepage. What is documented is historical: "Requires TerraBlender... for Minecraft 1.18 and above! It is not required for 1.17 and below, but in those versions you must use the Biomes O' Plenty world type when creating a new world!" — i.e. BOP's *own* dedicated world-preset only mattered pre-TerraBlender. [Source](https://modrinth.com/mod/biomes-o-plenty)
- **Compat-library search (question G):** no dedicated mod was found whose specific, stated purpose is "bridge an arbitrary third-party `ChunkGenerator` to TerraBlender." TerraBlender's own current mixin package (default branch, `26.3`) includes `MixinChunkGenerator.java`, `MixinChunkGeneratorBiomeSource.java`, `MixinMultiNoiseBiomeSource.java`, `MixinParameterList.java`, among others (filenames confirmed via GitHub contents API); a historical changelog entry ("Removed now unnecessary chunk generator mixin," v1.19.2-2.0.1.136) confirms TerraBlender has previously carried, and iterated on, chunk-generator compatibility shims internally rather than via an external bridge mod. [Source](https://modrinth.com/mod/terrablender/version/2.0.1.136) Lithostitched's own description states it "adds many new density function types (including Fast Noise!) and an injection system to apply terrain changes in a compatible manner" and lets mods "place your biome with biome injectors, a simple solution to modded biome layouts" [Source](https://modrinth.com/mod/lithostitched) — Lithostitched (and a third, less-documented library "Biolith" mentioned in Tectonic's own compatibility notes) function as an alternative, datapack-driven injection layer parallel to TerraBlender, for combining datapack-style worldgen mods with each other — not a literal bridge to an arbitrary custom Java `ChunkGenerator`.

### Inferences
- A plausible reconciliation of the two conflicting Terralith findings above (not independently verified, offered as a hypothesis only): MC-260949-class bugs are commonly about *loading order/crash* behavior when datapacks are combined with non-default `WorldPreset`s, not about which terrain actually renders. Given Terralith's jar ships **zero** mixins (Key Question 2) and no `large_biomes.json`/`amplified.json` override files, "supporting" these presets as of 2.6.0 most plausibly means *the world successfully generates without crashing/refusing* when Large Biomes/Amplified is selected alongside Terralith — using the density-function hybrid described above — rather than "Terralith's full custom terrain and ~100 biomes appear under Large Biomes/Amplified." This reconciles both pieces of verified evidence but should be treated as inference, not fact, until Terralith's actual world-preset-related code (if any) is read directly.
- Given the closed, unresolved Tectonic issue about `xz_scale` edits having no effect when combined with Terralith, and Tectonic's silence on world presets generally, it's plausible Tectonic's own preset behavior is entirely subordinate to whichever noise-settings file "wins" between its base pack, its Terralith-aware `overlay.terratonic*`, and any user-selected preset — but this is speculation absent a direct statement or code read.
- The consistent message across every mod checked in this section ("biome-adding datapacks are typically not compatible," "will likely not work well... unless compatibility was brought by either side through an addon or update," Tectonic/BOP's silence, the closed unresolved Tectonic issue) is that **none of these mods' authors consider generic third-party compatibility a supported goal** — every real compatibility path found in this entire research task (TerraBlender regions, Lithostitched biome injectors, Tectonic's `overlay.terratonic`) is pairwise and requires the *terrain mod's own author* to explicitly know about and support the other side. A new simulation-driven generator should expect to get **none** of this compatibility for free from any of these mods' existing infrastructure, regardless of which option (i or ii) it picks — the choice of option (i) vs (ii) only determines whether *existing* mixin/instanceof-gated mechanisms (TerraBlender, Lithostitched) keep firing, not whether Terralith/Tectonic/BOP would recognize the new generator as a peer.

### Gaps
- Whether Terralith's Java code contains any world-preset-related logic (a `WorldPreset` mixin, a custom preset-selection UI hook, etc.) that would explain its Large-Biomes/Amplified support claim was not directly checked — Terralith's decompiled class list (Key Question 2) shows no obviously-named such class, but this was not exhaustively ruled out.
- Tectonic's "General FAQ" and "Terratonic FAQ" wiki pages could not be fetched (load errors on every attempt) and may contain a direct answer to the world-preset question that this research could not access.
- No statement on world-preset compatibility for Biomes O' Plenty was found; this is "not found," not "confirmed no issue" — a targeted read of BOP's GitHub issue tracker (only its Modrinth/CurseForge/wiki pages were checked) might surface one.
- "Biolith," mentioned only in passing by Tectonic's own compatibility notes as a second biome-injection system alongside TerraBlender, was not independently researched at all.

## Synthesis — categorized worldgen-integration mechanisms and survival under option (i) vs option (ii)

### Takeaway
Across every mod examined in this research, all Overworld-integrated worldgen-compatibility mechanisms reduce to exactly **six** categories. Four of the six are graded purely by whether the concrete vanilla classes (`NoiseBasedChunkGenerator`, `MultiNoiseBiomeSource`, `Climate.ParameterList`, `ChunkGenerator`) remain in use — which is precisely what distinguishes option (i) from option (ii) — while two (biome modifiers, and dimension-scoped mechanisms) are essentially option-agnostic.

### Cited Findings — the six mechanisms, their concrete evidence base, and survival verdicts

| # | Mechanism | Concrete example(s) verified in this research | Survives option (i)? | Survives option (ii)? |
|---|---|---|---|---|
| 1 | **Biome placement as new parameter points in the vanilla 6-D multi-noise space**, merged into the *same* registry object other mods/vanilla use | TerraBlender `Region.addBiomes` (Java, R-tree-per-region on top of a shared codec point); Lithostitched `lithostitched:biomes`/`replace_fully` biome-injector (JSON, codec-level merge) — both keyed to Question 1/2 | Yes — the mechanism only needs `MultiNoiseBiomeSource`/`Climate.ParameterList` to remain the concrete classes consulted; simulation-fed climate values change *which* parameter point wins, not whether the merge machinery runs | No — both TerraBlender's and Lithostitched's merge mixins target the concrete classes by name; a from-scratch `BiomeSource` never triggers them (silently inert, not a crash), unless the replacement itself is/wraps `MultiNoiseBiomeSource` |
| 2 | **Density-function / noise-settings overrides** at the same vanilla resource ID (whole-file replacement, no deep merge) | Terralith's/Tectonic's full `overworld.json` + `density_function/overworld/*` replacements (Question 2); Terralith's Skylands spline; floating-island datapacks (Question 4A) | Conditional / collision risk — a simulation-driven option (i) generator that also needs to control these exact JSON resource IDs (to inject its own climate/density values) collides outright with any other mod claiming the same IDs; datapack JSON does not deep-merge, so whichever pack loads last wins entirely | No, unless the custom generator specifically still parses vanilla `noise_settings`/`density_function` JSON at those resource IDs — a bespoke procedural implementation gives such overrides nothing to attach to |
| 3 | **Configured/placed features attached to biomes, including via NeoForge biome modifiers** (`neoforge:add_features`/`remove_features`/`add_carvers`/etc.) | Create's `zinc_ore`/`striated_ores_*` (Question 5); Terralith ReStoned's same-ID `placed_feature` overrides (Question 2); YUNG's Better Caves' carver hook (Question 4D, carver-specific) | Yes — biome modifiers operate on `BiomeGenerationSettings`, populated once per biome independent of which `ChunkGenerator` is in use | Yes, for ordinary features/carvers — *unless* the custom generator skips vanilla's standard feature-placement or `applyCarvers()` pipeline steps entirely, which is a real, concrete risk for a from-scratch implementation (flagged explicitly for YUNG's Better Caves, Question 4D) |
| 4 | **Structures** (structure sets / jigsaw / structure processors) | YUNG's structure-mod family (Question 4D); Terralith's `disable.custom_structures` structure-set toggles (Question 2); Deeper and Darker's Ancient-City portal insertion (Question 4C) | Yes — structure placement is governed by `StructureSet`/biome tags, independent of the specific climate values a simulation feeds in | Yes, *unless* the custom generator omits vanilla's standard structure-placement pipeline — same caveat as row 3 |
| 5 | **Separate custom dimension** (own `DimensionType`, own generator+biome-source instance, own noise settings) | Deeper and Darker's "Otherside" (Question 4C); The Aether (Question 4E) — both confirmed built on vanilla's **generic**, data-driven `minecraft:noise`+`minecraft:multi_noise` types, no bespoke Java `ChunkGenerator` needed | Yes, unconditionally — never touches the Overworld's generator | Yes, unconditionally — same reason. Only indirect risk: if the dimension's sole access point is a structure (e.g. a portal in an Ancient City) that a from-scratch option (ii) generator fails to place, access is cut off even though the dimension itself is untouched |
| 6 | **Mixins directly into `ChunkGenerator`/`NoiseBasedChunkGenerator`/`NoiseChunk`/biome-source classes** | TerraBlender's 11 mixins (Question 1); Lithostitched's ~50 mixins (Question 2); Tectonic's 13 mixins (Question 2); Alex's Caves' `MultiNoiseBiomeSourceMixin` (Question 4B) | Yes — this is precisely what option (i) is defined to preserve (the concrete classes stay in use; only their data inputs change) | No, for mixins targeting **concrete** classes (`MultiNoiseBiomeSource`, `NoiseBasedChunkGenerator`, `Climate.ParameterList`) — silently inert under a true replacement. Mixins targeting the **abstract** `ChunkGenerator` base (TerraBlender's `MixinChunkGenerator`, disabling `validate()`) would likely still attach, since any custom generator must still subclass it to be constructible through Minecraft's codec/registry system |

### Inferences
- Rows 3, 4, and 5 are structurally different from rows 1, 2, and 6: they do not depend on which concrete `ChunkGenerator`/`BiomeSource` classes are chosen, so they are close to "free" compatibility wins for a simulation-driven generator under *either* option — provided the generator's implementation (for option ii specifically) is careful to still invoke vanilla's standard structure-placement and feature/carver pipeline steps rather than reimplementing terrain shaping in a way that bypasses them.
- Rows 1, 2, and 6 are exactly where option (i) vs option (ii) is decisive, and they cover the large majority of what makes Terralith, Tectonic, TerraBlender-based biome mods (BOP, BWG), and Lithostitched-based mods (Regions Unexplored) function at all. Choosing option (ii) (a fully custom `ChunkGenerator`/`BiomeSource`) means accepting that **all** of these mods' terrain/biome contributions go silently inert simultaneously, as a single architectural consequence — not something fixable mod-by-mod — unless the replacement is deliberately built to still subclass/wrap `NoiseBasedChunkGenerator` and `MultiNoiseBiomeSource` (in which case it is, functionally, option (i) with extra steps).
- No mechanism found anywhere in this research offers a generic, forward-compatible way for a *new, unknown* mod to be recognized by Terralith, Tectonic, TerraBlender, or Lithostitched — every real cross-mod compatibility path documented (TerraBlender regions/weights, Lithostitched biome injectors, Tectonic's `overlay.terratonic`) requires the terrain mod's own author to have shipped code/data keyed to the *other* mod's specific ID in advance. This is independent of the option (i)/(ii) choice: it means a simulation-driven generator's compatibility strategy cannot rely on "being noticed" by these mods' own infrastructure, only on preserving the concrete classes/pipeline steps (rows 1–6 above) that let their *existing*, class-targeted mechanisms keep firing.

### Gaps
- This categorization covers only Overworld-integrated (and, for row 5, dimension-level) mechanisms actually observed in the mods researched; it does not claim to be an exhaustive taxonomy of every possible worldgen-integration technique in the broader NeoForge modding ecosystem.
- No empirical/in-game test of any option (i) or (ii) scenario was performed (explicitly out of scope per constraints — no game launches or Gradle builds); every survival verdict above is derived from static analysis of class/method targets and codec/registry structure, not observed runtime behavior.

## Follow-up (coordinator question) — does `GeologicChunkGenerator extends NoiseBasedChunkGenerator` (custom NoiseRouter reading simulation rasters, registered under a new WorldPreset) preserve TerraBlender's region/surface-rule injection and Lithostitched's injection systems? What exactly do they key on, and does a new settings key like `mymod:geologic_overworld` lose BOP/BWG/RU biomes/rules?

### Takeaway
**Neither TerraBlender nor Lithostitched keys on the `NoiseGeneratorSettings` resource key/holder identity or on the `multi_noise_biome_source_parameter_list` preset ID — a name like `mymod:geologic_overworld` for the settings holder is, by itself, completely safe and does not cause anything to be lost.** TerraBlender keys on (1) the LevelStem's **`DimensionType`** being tagged into the data-driven `terrablender:overworld_regions`/`nether_regions` tags, plus (2) `instanceof NoiseBasedChunkGenerator` and (3) biome source `instanceof MultiNoiseBiomeSource` — all three are satisfied by the proposed design as described, **provided the new WorldPreset's overworld `LevelStem` still uses the vanilla `minecraft:overworld` `DimensionType`** (or a custom one added to that tag with one line of datapack JSON) and **provided the "kept" `MultiNoiseBiomeSource` is the actual shared/merged object** (not a fresh disconnected instance). Lithostitched's surface-rule/worldgen-modifier registry is explicitly scoped by **`ResourceKey<LevelStem>`** (a `levels` field), and its biome-injector JSON is scoped by a **dimension key** — both are satisfied the same way, by keeping the LevelStem at the conventional `minecraft:overworld` ID. **A real, shipped 1.21.1 NeoForge mod doing almost exactly this design (custom-DensityFunction-based terrain reading pre-simulated tile data, no custom `ChunkGenerator`/`BiomeSource`) exists and was found and inspected: ReTerraForged (`Campione01/ReterraForged`, MC 1.21.1, NeoForge 21.1.201) ships a dedicated, TerraBlender-conditional Mixin compat layer that is direct, working proof of concept for exactly this integration**, including the specific technique of redirecting TerraBlender's own region-selection call to read a simulation-derived value instead of TerraBlender's built-in noise.

### Cited Findings

**What TerraBlender keys on — direct answer to each of the four options posed:**
- ❌ **Not** the `minecraft:overworld` noise-settings resource key or holder. Grepping every decompiled TerraBlender source file for the literal string `"minecraft:overworld"` found exactly one occurrence, in `terrablender.worldgen.DefaultOverworldRegion` — only the display name of TerraBlender's own built-in fallback `Region` (shown in the F3 debug line), not a check against any `NoiseGeneratorSettings` key `(established in Key Question 1, both via direct GitHub source read of `Common/src/main/java/terrablender/worldgen/DefaultOverworldRegion.java` and independent decompilation of the released `terrablender-4.1.0.8.jar`)`.
- ❌ **Not** the `minecraft:overworld` `multi_noise_biome_source_parameter_list` preset ID either — no reference to `Registries.MULTI_NOISE_BIOME_SOURCE_PARAMETER_LIST` or that registry's `minecraft:overworld` entry appears anywhere in TerraBlender's own code. (That specific lookup — `MultiNoiseBiomeSourceParameterLists.OVERWORLD`, i.e. resource key `minecraft:overworld` in the *parameter-list* registry — is done by **Lithostitched's** `MNBSMixin`, a completely different library, for its own migration-biome merge trick; see Key Question 2 and below. Do not conflate the two libraries' keying mechanisms.)
- ✅ **the overworld LevelStem/dimension** — correct in substance, but the precise mechanism is one level more specific: TerraBlender's `terrablender.util.LevelUtils.getRegionTypeForDimension(Holder<DimensionType>)` takes the LevelStem's **`DimensionType`** (via `levelStem.type()`) and returns `RegionType.OVERWORLD`/`NETHER` only if that `DimensionType` is a member of the datapack tag `terrablender:overworld_regions` / `terrablender:nether_regions` (default data: `{"replace": false, "values": ["minecraft:overworld"]}` / `["minecraft:the_nether"]`) — otherwise it returns `null` and **no region blending or surface-rule injection happens for that dimension at all**. Because the tag has `"replace": false`, any datapack (including a new mod's own) can add a new `DimensionType` ID to it. `(Key Question 1, decompiled `terrablender-4.1.0.8.jar`: `LevelUtils.java`, `DimensionTypeTags.java`, and the tag JSON.)`
- ✅ **`instanceof NoiseBasedChunkGenerator`** — confirmed required, together with biome source `instanceof MultiNoiseBiomeSource` (`TheEndBiomeSource` is special-cased separately and unconditionally). This is `shouldApplyToChunkGenerator`'s check, per the same decompiled source. `GeologicChunkGenerator extends NoiseBasedChunkGenerator` satisfies this by construction.

**Applying this to the proposed `GeologicChunkGenerator` design:**
- The design keeps "the overworld's (possibly modded) MultiNoiseBiomeSource" and extends `NoiseBasedChunkGenerator` — conditions 2 and 3 above are satisfied by definition, **as long as "keep the MultiNoiseBiomeSource" means reusing the actual shared Java object/registry entry** that TerraBlender has already merged BOP/BWG/etc.'s `Region`s into (TerraBlender's per-dimension initialization, `LevelUtils.initializeOnServerStart`, iterates every `Registries.LEVEL_STEM` entry at server start and calls the `Climate.ParameterList` mixin's `initializeForTerraBlender` on whichever parameter-list object is attached there — so it is *the object*, not any particular resource key, that ends up carrying the merged region data).
- The remaining condition (DimensionType tag membership) depends entirely on what `DimensionType` the new WorldPreset's overworld `LevelStem` uses — **not** on the `NoiseGeneratorSettings` key. If the new preset's overworld entry still uses vanilla's own `minecraft:overworld` `DimensionType` (the natural choice if height limits/ambient light etc. are unchanged from vanilla), the tag check passes automatically with zero extra work, because `minecraft:overworld` is already in `terrablender:overworld_regions` by default. If a custom `DimensionType` is needed (e.g. because the simulated world has different height limits), it must be added to that tag via one `"replace": false` datapack JSON file — trivial, and something the new mod itself can ship (it does not require any cooperation from TerraBlender's author).
- **Conclusion: a new `NoiseGeneratorSettings` resource key such as `mymod:geologic_overworld` does not, by itself, cause BOP/BWG/Regions-Unexplored-via-TerraBlender biomes or surface rules to be lost.** What would cause a loss is (a) the new WorldPreset's `LevelStem` using an untagged `DimensionType`, or (b) the "kept" `MultiNoiseBiomeSource` actually being a fresh, disconnected instance rather than the real shared/merged one.

**Lithostitched — same question, its own keying mechanism (Key Question 2 detail, re-applied here):**
- Its surface-rule/worldgen-modifier registry entries (`AddSurfaceRuleModifier`, decompiled in Key Question 2) are typed `record AddSurfaceRuleModifier(..., List<ResourceKey<LevelStem>> levels, ...)` — explicitly scoped by **`ResourceKey<LevelStem>`** (e.g. `minecraft:overworld`), **not** by the `NoiseGeneratorSettings` key. As long as `GeologicChunkGenerator`'s WorldPreset produces its overworld content under the conventional `LevelStem` key `minecraft:overworld` (the normal, expected shape of a "WorldPreset" that is meant to still *be* the Overworld), any `levels: ["minecraft:overworld"]`-scoped modifier from Regions Unexplored/Terralith/Tectonic resolves correctly regardless of the settings-holder's own resource name.
- Its biome-injector JSON (`lithostitched:replace_fully` etc., Key Question 2) is scoped by a `"dimension"` field (observed value `"minecraft:overworld"` in Terralith's own use of it) — same conclusion, provided that field resolves against the dimension/LevelStem key rather than the noise-settings key (the exact Java field type — `ResourceKey<Level>` vs `ResourceKey<LevelStem>` vs `ResourceKey<DimensionType>` — was not independently decompiled; see Gaps).
- Its core biome-list-merging trick (`MNBSMixin`/`MNBSPLMixin`, Key Question 2) hardcodes a lookup of the Java constant `MultiNoiseBiomeSourceParameterLists.OVERWORLD` — vanilla's own fixed resource key `minecraft:overworld` **inside the `multi_noise_biome_source_parameter_list` registry specifically** (a third, separate registry from both `noise_settings` and `LevelStem`). This resolves correctly as long as the biome source's parameter list is (or references) that same canonical `minecraft:overworld` parameter-list entry — again independent of the `NoiseGeneratorSettings` key name.
- **Conclusion: Lithostitched's mechanisms are keyed on the `LevelStem`/dimension key and on the `multi_noise_biome_source_parameter_list` registry's `minecraft:overworld` entry — never on the `NoiseGeneratorSettings` key. The same `mymod:geologic_overworld` settings-key choice that is safe for TerraBlender is equally safe for Lithostitched**, under the same proviso (the overworld `LevelStem` key and the biome-parameter-list identity stay conventional).

**ReTerraForged (`Campione01/ReterraForged`, MC 1.21.1, NeoForge 21.1.201, mod version 0.0.6) — a real, shipped precedent for exactly this architecture:**
- Confirmed via `gradle.properties`: `minecraft_version=1.21.1`, `neoforge_version=21.1.201` `(verified: GitHub, repo `Campione01/ReterraForged`, branch `main`, file `gradle.properties`)`. Note on naming: there is no project literally named "ReTerraForged" on Modrinth (`api.modrinth.com/v2/project/reterraforged` → HTTP 404); the GitHub ecosystem around the original `TerraForged`/`racoonman2/ReTerraForged` (which itself tops out at MC 1.20.2, not 1.21.1) has fragmented into several forks, of which `Campione01/ReterraForged` is the one that actually targets MC 1.21.1/NeoForge, and whose Java package (`raccoonman.reterraforged`) shows it is a continuation of the same codebase lineage. A separate, unrelated MC-1.21.1-NeoForge project, `Sammasr/terrascribe` ("simulated-erosion heightmap, flow-based rivers, climate-driven biomes"), was also found in this same search and is flagged here only as a pointer for the prior-art research thread — it was not investigated further as it is out of this task's scope.
- Its own worldgen is built on custom `DensityFunction` types reading a precomputed per-chunk "Tile"/"Cell" cache — `world/worldgen/densityfunction/CellSampler.java` is a `record CellSampler(Supplier<WorldLookup> deferredLookup, Field field) implements MarkerFunction.Mapped`, whose `Field` enum (`CONTINENT`, and others including a biome-region field) reads values out of a `Cell` object populated by `WorldLookup.applyCell(...)` from the mod's own simulated tile data — i.e., **exactly** the "custom `DensityFunction` types reading simulation rasters" approach the coordinator's proposed design describes, already implemented and shipping `(verified: GitHub, `common/src/main/java/raccoonman/reterraforged/world/worldgen/densityfunction/CellSampler.java`)`.
- It has **no custom `ChunkGenerator` or `BiomeSource` subclass** for this — TerraBlender compatibility is handled entirely through **four Mixins that are conditionally applied only when TerraBlender is loaded**, gated by `TBCompat.isEnabled() = ModLoaderUtil.isLoaded("terrablender")` and an explicit list `TBCompat.TERRABLENDER_COMPAT_MIXINS` naming exactly `mixin.terrablender.{MixinClimateSampler, MixinNoiseChunk, MixinParameterList, MixinTargetPoint}` `(verified: GitHub, `world/worldgen/terrablender/TBCompat.java`, full file read)`.
- **The exact mechanism, read end-to-end from source:**
  1. `TBNoiseRouterData.bootstrap` registers a new `DensityFunction` at resource key **`terrablender:uniqueness`**, whose value is `RTFDensityFunctions.cell(CellSampler.Field.BIOME_REGION)` — i.e. a density function that reads ReTerraForged's own simulated/precomputed biome-region field, published under the `terrablender:` namespace `(verified: `data/worldgen/compat/terrablender/TBNoiseRouterData.java`, full file read)`.
  2. `MixinTargetPoint` (`@Mixin(Climate.TargetPoint.class)`) adds a mutable `uniqueness` field (default `NaN`) to vanilla's `Climate.TargetPoint`, via Mixin's `@Implements`/`@Interface` "soft implements" trick (no vanilla method signatures are touched, just a new interface + field bolted on).
  3. `MixinClimateSampler` (`@Mixin(Climate.Sampler.class)`) injects at `RETURN` of `Climate.Sampler.sample(x,y,z)` (capturing the internal `DensityFunction.SinglePointContext` local), and if a `uniqueness` `DensityFunction` has been set on this sampler, computes it at that point (`this.uniqueness.compute(ctx)`) and writes the result onto the just-created `TargetPoint` via the interface added in step 2.
  4. `MixinNoiseChunk` (`@Mixin(NoiseChunk.class)`) injects at `RETURN` of `cachedClimateSampler(...)`: if both the newly-built per-chunk sampler and the level-wide `RandomState`'s global sampler implement the "has uniqueness" interface, it takes the *global* `terrablender:uniqueness` density function, passes it through `NoiseChunk`'s own private `wrap(DensityFunction)` method (the same per-chunk caching/interpolation wrapper vanilla applies to every other density function consumed during chunk generation), and attaches the wrapped copy to the per-chunk sampler — i.e. it plumbs the registered `terrablender:uniqueness` function down to chunk-local evaluation using completely standard vanilla machinery.
  5. **`MixinParameterList` (`@Mixin(Climate.ParameterList.class)`) is the payoff**: it `@Redirect`s the internal call to `getUniqueness(x,y,z)` made *inside TerraBlender's own* `findValuePositional` method (the exact method documented in Key Question 1 that picks which `Region`'s R-tree to search). If the `Climate.TargetPoint` being resolved carries a non-`NaN` uniqueness value (i.e., steps 1-4 successfully computed one from the simulated `BIOME_REGION` field), it converts that `[0,1]`-ish value into a discrete region index (`NoiseUtil.round(this.maxIndex * uniqueness)`, where `maxIndex = Regions.getCount(regionType) - 1`) and returns that **instead of** letting TerraBlender fall through to its own built-in 2-D Area/zoom-noise `getUniqueness(x,y,z)` algorithm. If the value is `NaN`, or the column is "underground" (`depth ≥ 0.2`, or below Y 48 with a cave-biome-compat mod present), it explicitly falls back to calling TerraBlender's original `getUniqueness(x,y,z)` unmodified `(verified: GitHub, `mixin/terrablender/MixinParameterList.java`, full 314-line file read)`.
  - **In plain terms: ReTerraForged makes its own simulated biome-region raster *become* the signal TerraBlender uses to decide "which mod's Region owns this location," instead of letting TerraBlender's independent pseudo-random tessellation decide — while transparently falling back to TerraBlender's normal behavior wherever the simulation doesn't have an opinion (underground).** This is a direct, working, shipped answer to "can a simulation-driven generator make TerraBlender-based mods (BOP, BWG, etc.) read from the simulation's own geography rather than TerraBlender's own noise" — yes, via exactly this Mixin-redirect-on-the-internal-call pattern, and only when TerraBlender is present (soft dependency, same pattern Lithostitched uses for its own optional TerraBlender compat shim, Key Question 2).
- ReTerraForged also has bespoke, hardcoded, pairwise compat for two specific TerraBlender-based cave-biome mods by name — `darkerdepths:overworld` and `deeperdarker:overworld` region IDs are looked up via `Regions.getIndex(regionType, name)` and given special handling for underground columns — reinforcing the Key Question 6 synthesis finding that **even this unusually compat-conscious mod still needs to hardcode specific other mods' IDs in advance**; there is no generic mechanism that would extend automatically to a brand-new, unknown mod.
- **No Lithostitched compat of any kind was found anywhere in ReTerraForged's source tree** (an exhaustive filename grep for "lithostitched" across all 681 tracked files returned nothing). This is a useful negative data point: Lithostitched's dependent mods (Terralith, Tectonic, Regions Unexplored) are themselves full terrain-shape replacements at the same `overworld.json`/density-function resource IDs a mod like ReTerraForged also needs to control — i.e., they are mutually-exclusive alternatives to ReTerraForged's own terrain generation, not layerable on top of it, which is presumably why no compat shim exists for that direction.

### Inferences
- The general pattern ReTerraForged demonstrates — "redirect the specific internal call inside the dependency's own method via a conditionally-applied Mixin, and source the value from your own simulation data, falling back to the dependency's default behavior when your data doesn't cover a case" — is the same shape of solution already seen twice in this research (Lithostitched's optional `compat/terrablender/NoiseBasedChunkGeneratorMixin`, Key Question 2, and now ReTerraForged's four TerraBlender mixins). This suggests it is the *established idiom* for this specific compatibility problem in this modding ecosystem, not a one-off — a `GeologicChunkGenerator`-based mod could adopt the identical technique (a small, TerraBlender-presence-gated Mixin module shipped by the new mod itself) with high confidence it will work, since it is now evidenced by two independent implementations rather than one.
- Because TerraBlender's gate is the `DimensionType` tag (not the dimension/LevelStem resource key itself, and definitely not the noise-settings key), the safest concrete recommendation is: keep the new WorldPreset's overworld `LevelStem` at the conventional key `minecraft:overworld`, keep its `DimensionType` as vanilla's `minecraft:overworld` unless a genuine reason forces a new one (in which case add one `"replace": false` tag-extension JSON), and keep the `MultiNoiseBiomeSource` as the literal shared/merged object — none of which constrains what the new `NoiseGeneratorSettings` holder is called.

### Gaps
- Lithostitched's `biome_injector` JSON's `"dimension"` field was only observed as a raw JSON string (`"minecraft:overworld"`); the exact Java field type behind it (`ResourceKey<Level>` vs `ResourceKey<LevelStem>` vs `ResourceKey<DimensionType>`) was not independently decompiled, so the claim that it behaves like the `AddSurfaceRuleModifier`'s `LevelStem`-keyed scoping is an inference from the shared "minecraft:overworld" convention across all three registries, not a directly-confirmed field type.
- ReTerraForged's own "Preset"/`WorldPreset` registration code (how it actually gets offered as an option in the vanilla world-creation screen, and whether its overworld `LevelStem` is registered at the conventional `minecraft:overworld` key or a different one) was not read — only its `PresetDimensionTypes.java` file's existence was confirmed, not its contents. This matters because ReTerraForged's own answer to "does it keep the LevelStem key conventional" was not directly verified, only inferred from the fact that its TerraBlender compat evidently works for it in practice (implied by the diagnostic logging built into `MixinParameterList`, which would be dead code if the compat path were never reached).
- Whether TerraBlender's per-dimension initialization (`LevelUtils.initializeOnServerStart`) would run correctly if the new WorldPreset's LevelStem is created fresh at world-creation time (rather than being one of the datapack-registered LevelStem entries present at server-start registry-load time) was not tested — the mechanism iterates `Registries.LEVEL_STEM`, which is populated from the world's own generated registry data at load time, so this should work the same way for any world regardless of which WorldPreset produced it, but this was reasoned from the mechanism's description rather than observed directly.
